# E9f — hardened final children для двух BX-генераторов

Разрешён только раздел1 [roadmap](<../../RESEARCH_ROADMAP_20261101.md>). [Текущие результаты](<RESULTS.md>), [неизменяемые интерпретации/журнал](<JOURNAL.md>), [протокол](<PROTOCOL.md>). Старые checkpoints не изменяются. Отрицательный итог относится только к32 перечисленным tuple.

Оркестратор вWSL Ubuntu-24.04 из этой папки:

> Исполняемый код/команды опущены в документационной копии.


Первая команда проверяет аудит предшествующих проходов, принимает обе версии, запускает полные проходы последовательно и проверяет результат. Повторный запуск использует зафиксированные входы и готовые блоки; SERIES.lock запрещает второй процесс. PROCESS.json сохраняетPID, время, boot_id и/proc/stat для идентификации. Если процесс жив, резервная автоматизация не должна запускать ещё один экземпляр. Финальное подтверждение обеих серий — COMPLETE.json плюс два FULL_AUDIT.json; один STATUS=complete без этих сертификатов недостаточен.

Подготовка выполнена отдельно: setup.py вWindows Python3.11 venv создал версии16807/48271. Каждый cpu/search.cpp собирается g++ -O3 -march=native -std=c++17 -fopenmp -Wno-deprecated-declarations с-lsecp256k1 -lcrypto. prepare.py и batch_check.py prepare запускаются вWindows venv после CPU-сборки, затем bash build.sh вWSL. Не пересоздавать эти файлы после принятия: изменения требуют новой версии.

Контроли/пилоты отдельно: python3 accept_core.py 16807, затем48271. Аудит старых проходов: python3 audit_previous.py (вWSL: сохранённые старые manifest содержат абсолютные/mnt/c пути). Он только читает старые каталоги.

Для остановки создать пустой файлSTOP в корне серии. При полном проходе оркестратор передастSTOP текущему worker, который сохранит завершённые блоки и выйдет. Для продолжения после выяснения причины удалить только эти STOP-файлы в новой серии и повторить run_series_v2.py. Кандидата/ошибку автоматически не обходить. Не редактировать старые checkpoints, не считать ошибку отрицательным результатом. После исправления гонки чтения статуса03:37 актуальны RUN_INPUTS_v2.json и корневые stdout-v2.log/stderr-v2.log; исходная обвязка сохранена для аудита. Дочерние журналы по-прежнему stdout.log/stderr.log.

Нет аренды облака, BIP44, других длин entropy или иных пунктов roadmap. Компьютер должен оставаться включённым. Принятые файлы каждого ядра заморожены FINAL_MANIFEST.json; root RESULTS.md обновляется каждые10 секунд во время полного прохода.
