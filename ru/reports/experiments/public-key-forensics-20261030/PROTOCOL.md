# E5 — публичные ключи и подписи puzzle: границы исследования

Зафиксировано 2026-10-30 до анализа байтов транзакций. Только чтение публичных
данных; без подписания/рассылки транзакций и без изменения поисковых проектов.

## Вопросы

1. Найден ли проверяемый публичный ключ, HASH160 которого соответствует адресу
   №71 `1PWo3JeB9jrGwfHDNpdGK54CRas7fsVzXU`?
2. Какие публичные ключи действительно раскрыты входами транзакций, связанных
   с исходными 256 выходами? Какие известны только из опубликованных решений?
3. Есть ли повторяющиеся ECDSA r среди проверенных подписей; одинаковы ли ключи,
   сообщения и s? Отличать повтор подписи от потенциального повторения nonce.
4. Для уже опубликованных полных приватных ключей проверить точное соответствие
   nonce стандартному RFC6979/HMAC-SHA256 без дополнительной энтропии; учитывать
   эквивалентность k и n−k при нормализации s. Это отпечаток способа подписания,
   не доказательство семейства кошелька или генерации ключей в 2015 году.

## Конечный набор источников и раскрываемое покрытие

- Пять транзакций-ориентиров: исходная 2015, перераспределение 2017, малые
  поступления 2019, расходование 2019, пополнение 2023. Ссылки третьих сторон —
  только средство найти txid. Данные берутся из Esplora API Blockstream/mempool.space.
- Восстановить 256 адресов по исходным выходам. Номера 1–160 сверить с сохранённой
  таблицей, уже проверенные 83 решения — с соответствующими публичными ключами.
- Получить outspends всех 256 исходных выходов и транзакции их непосредственного
  расходования. Это конечный граф, не полный обход истории всех 256 адресов.
- Для №71 отдельно получить адресную статистику, всю доступную подтверждённую
  историю с пагинацией (до 100 страниц по 25), mempool и UTXO; сравнить два источника.
  Это снимок текущих провайдеров, не архив когда-либо удалённых mempool-транзакций.
- Просмотреть закреплённые открытые таблицы и первичные форумные сообщения;
  любые найденные SEC-точки проверять математически и по точному HASH160.
  Не считать слово «public key» на сайте доказательством существования точки.
- Для проверки подписей загружать исходные родительские транзакции подходящих
  входов (puzzle-входы и все входы пяти ориентиров). Прочие входы прямых расходов
  классифицируются отдельно, без попытки восстановить чужие приватные ключи.
- Защитный предел 600 успешных HTTP-загрузок и 30 минут сетевого wall time.
  Лимиты, ошибки, неподдержанные скрипты и неполное покрытие явно сохранять.

## Проверки

Сохранять URL, время, SHA-256 и исходный ответ каждой загрузки, включая ошибки.
Рассчитать txid по сериализации без witness; сверить поля JSON с raw. Для ключа
проверить точку secp256k1, HASH160 и scriptPubKey расходуемого родительского выхода.
Не принимать публичный ключ одного из отправителей входящего перевода за ключ №71.

Поддержать legacy P2PKH, P2WPKH и nested P2SH-P2WPKH: DER, sighash ALL/NONE/SINGLE,
ANYONECANPAY, исторический SIGHASH_SINGLE out-of-range. Для witness использовать
BIP143 и проверенную сумму родительского выхода. Multisig/P2WSH/Taproot и прочие
скрипты явно выделять как неподдержанные этой стадией. Проверить подписи coincurve
и независимой Python-арифметикой; оригинальный high-S сохранять, для проверки
libsecp256k1 допускать эквивалентную нормализацию s.

До анализа: контроль сериализации/txid, положительные и отрицательные подписи,
ошибочный prevout/pubkey/message, повтор r с одинаковым/разным сообщением,
low-S/high-S, официальные векторы sighash Bitcoin Core и BIP143.
RFC6979 сверить с coincurve на синтетических ключах/сообщениях. Основную проверку
ограничить точной конфигурацией без подбора дополнительной энтропии и grinding;
несовпадение не исключает другие варианты детерминированной подписи.
Повтор r при одном публичном ключе и разных сообщениях помечать кандидатом
слабости; вывод о восстановимости делать только после дополнительной проверки.
В этой стадии не запускать массовые lattice-атаки и не выводить «плохой nonce»
из распределения нескольких подписей. Известные решения используются как
контроль, а не для получения доступа к посторонним адресам.

## Атрибуция и вывод

Разделять: доказанный расход конкретного выхода; совместный контроль ключей,
следующий из подписей; гипотезу о связи транзакций с создателем; заявление аккаунта
на форуме. Подпись решателя не является свидетельством программы генерации
создателя. Совместное расходование не доказывает, что подписывал один человек.

Если ключ №71 не найден, вывод только «не найден в указанном покрытии», а не
доказательство отсутствия любых публикаций. Если найден, независимо проверить
точное соответствие адресу; запуск kangaroo — отдельный следующий этап.
Сохранять код, данные, checkpoints, каталог JSON/CSV, отчёт, журнал и команды
продолжения/пересборки без повторных сетевых обращений.
