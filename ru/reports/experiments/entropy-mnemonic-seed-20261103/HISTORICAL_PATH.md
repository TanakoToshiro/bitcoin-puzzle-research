# Исторический маршрут BX 2.0.0

03.11.2026, Europe/Moscow. **Предложенная цепочка BX → BIP39 → PBKDF2
не подтверждена: у проверенных команд BX 2.0.0 другой алгоритм.** Это результат
проверки полного дерева, вызываемых функций и исходных тестов, а не вывод из 404.

## Реальные команды и байты

В src/generated.cpp зарегистрированы `mnemonic-encode` и `mnemonic-decode`.
Обе реализации прямо оставляют переход с Electrum на BIP39 в TODO.
Их заголовки описывают Electrum. Имена mnemonic-new/mnemonic-to-seed не найдены
ни в полном дереве этого commit, ни в реестре его команд.
[Encoder](https://github.com/libbitcoin/libbitcoin-explorer/blob/aae99b278fdbfa31005cfa083ccbbf909212cbe4/src/commands/mnemonic-encode.cpp),
[decoder](https://github.com/libbitcoin/libbitcoin-explorer/blob/aae99b278fdbfa31005cfa083ccbbf909212cbe4/src/commands/mnemonic-decode.cpp).

1. `seed` разрешает битовую длину ≥128, кратную 8; default 128. Windows RNG:
   одно uint32 → MT19937 → каждый выход `%255`. Seed 0 допустим.
2. `mnemonic-encode` получает base16, декодированный попарно в bytes. Регистр
   hex допускается любой; нечётное число hex-символов отвергается, leading zeros
   сохраняются, разворота нет. Команда требует ≥16 байт. Обе целевые длины,
   16 и 32, допустимы; верхнего ограничения BIP39 в этом коде нет.
3. `encode_mnemonic` сначала возвращает bytes в hex с двумя цифрами на байт,
   затем читает очередные 8 hex-цифр как uint32. Это BE-порядок 4-байтных блоков.
   Хвост в 1–3 байта игнорируется библиотекой. Для 16/32 хвоста нет.
4. Единственный фиксированный английский словарь содержит 1626 уникальных
   ASCII-слов. Для n=1626 и очередного x:

   ```text
   a = x mod n
   b = (floor(x/n) + a) mod n
   c = (floor(x/n²) + b) mod n
   ```

   Выход — слова a,b,c. Итого 12/24 слова, но это **не BIP39**. Checksum,
   SHA256 entropy-checksum и 11-битные индексы здесь отсутствуют.
5. Encoder соединяет слова одним ASCII-пробелом и завершает строку newline.
   ASCII одновременно является тем же UTF-8. В stdin-десериализации decoder
   разделители — LF, CR, TAB и space с token compression; слова затем ищутся
   буквальным сравнением std::string. Case folding/NFKD в этом пути нет.
6. Passphrase-параметра нет. Password, salt, PBKDF2 iterations и dkLen
   **не применимы**. Нельзя подставлять "mnemonic", 2048 и 64 из BIP39.
7. Decoder обрабатывает полные тройки, игнорирует остаток 1–2 слова, не проверяет
   словарь надлежащим образом (неизвестное слово даёт index=1626). В самом начале
   пишет дополнительный newline в std::cout. Возвращает конкатенацию hex chunks
   **без дополнения каждого chunk до 8 цифр**.
8. `hd-new` принимает hex→bytes и проверяет ≥16 байт. Именно эти bytes идут в
   HMAC-SHA512 с ключом ASCII `Bitcoin seed`; первые 32 байта — scalar, остальные
   32 — chaincode. Между decoder и HMAC PBKDF2 отсутствует.

[Library codec](https://github.com/libbitcoin/libbitcoin-system/blob/e44cc97bdd3fcd3d3c6c31b19f069a17fe3eb82f/src/wallet/mnemonic.cpp),
[base16](https://github.com/libbitcoin/libbitcoin-system/blob/e44cc97bdd3fcd3d3c6c31b19f069a17fe3eb82f/src/formats/base16.cpp),
[HD](https://github.com/libbitcoin/libbitcoin-system/blob/e44cc97bdd3fcd3d3c6c31b19f069a17fe3eb82f/src/wallet/hd_keys.cpp).

## Потеря ведущих нулей: почему нельзя объявить весь codec тождественным E15

Для корректных encoder-троек математический inverse восстанавливает uint32 x.
Однако вывод `ss << val` не сохраняет фиксированную ширину. Это потеря нулей
**каждого** блока, а не только начала всей entropy.

| Вход | Выход decoder | Следствие при передаче в hd-new |
|---|---|---|
| `baadf00d` ×4 | тот же hex | Те же 16 seed-байт, что в E15 |
| 16 нулевых байт | `0000` | 2 байта; отклоняется |
| `00112233` + `baadf00d` ×3 | `112233` + `baadf00d` ×3 | 15 байт; отклоняется |
| `00112233` + `baadf00d` ×7 | `112233` + `baadf00d` ×7 | 31 байт; допустимый изменённый seed |
| `01122334` + `baadf00d` ×7 | 63 hex-символа | Нечётный hex; отклоняется |

На сохранённых 136 RNG seed: для длины16 допустимы107, все сохраняют bytes;
27 дают нечётный hex,2 — слишком короткий seed. Для длины32:82 сохраняют bytes,
13 дают допустимый изменённый seed,41 дают нечётный hex. Это контрольная выборка,
не оценка долей всего uint32-домена. Все случаи совпали в Python и двух сборках
оригинального C++ исходника. Полные данные: CONTROL_TRACES.json — артефакт исходного исследования (`CONTROL_TRACES.json`; вне снимка).

Для целевых 16-байтных inputs любой принятый hd-new результат этой source-модели
равен исходному; для 32-байтных это неверно. Поэтому E15 относится к сохранённым
bytes и **не исключает** новую композицию с допустимым сокращённым32 seed.
Поиск этой отдельной ошибки кодека здесь не зарегистрирован и не выполнялся.

## BIP32 и границы композиции

`hd-private` явно задаёт индекс и hard flag; сам инструмент не выбирает все
40 исследовательских схем E15. Normal HMAC-message = compressed parent SEC ||
ser32_BE(index); hardened = 00 || ser256_BE(parent) || ser32_BE(index+2³¹).
Master проверяет secret через verify_private_key; child возвращает invalid
объект при отказе ec_add. В этих методах нет автоматического поиска следующего
индекса. Полный библиотечный invalid-EC аудит в текущей серии не повторялся.

Последовательность `seed → mnemonic-encode → mnemonic-decode → hd-new` можно
составить из реально существовавших интерфейсов. Она не доказывает сценарий
пользователя BX и не доказывает её применение автором Puzzle. Это source-backed
композиция старого codec, без PBKDF2. BIP44 — независимо составляемые HD-индексы,
а не признак наличия BIP39.

В bitcoinj0.12 BIP39/PBKDF2 уже подтверждён предыдущим аудитом. Импорт BX entropy
в другой исторический инструмент потребовал бы отдельной конкретной композиции
и нового протокола; автоматически менять основной кандидат на bitcoinj нельзя.
Наличие у библиотеки API для entropy — возможность программиста, а не свидетельство
такого пользовательского маршрута автора.

## Решение

Новая цепочка BX 2.0.0 → BIP39/PBKDF2 не прошла историческую проверку. CPU/GPU
поисковая реализация и пилот не запускаются; оценка стоимости полного домена
остаётся **не измерена**, а не нулевой. Доступный GPU не является препятствием.
Сохранён точный альтернативный source path и его leading-zero ограничение,
чтобы дальнейшее исследование не повторяло ошибочную предпосылку.
