# Второй заход №3 — история CoinVault и исполнение HDKeychain

02.11.2026. **Нового восстановления root или ускорения настоящего Puzzle №71 не получено.** Закрыто существенное ограничение первого захода: теперь исполнен скомпилированный исходный HDKeychain на308 случаях. Дополнительно проверены12 исторических редакций `hdkeys.cpp` и отдельный legacy CoinQ Vault. Ни в одном просмотренном переходе не обнаружена ранняя мультипликативная BIP32 или схема с известными из решений коэффициентами.

## Что сделано впервые

Скомпилированы неизменённые `hdkeys.cpp`, `hdkeys.h`, `BigInt.h`, `secp256k1.cpp` из commit ace0c828bed7441ef6ddda314674d882ecf4dbbe. Файлы проверяются побайтово с первым заходом. Использованы уже установленные WSL Ubuntu, g++13.3.0 и OpenSSL3.0.13. Общие пакеты/окружения не менялись.

Адаптация ограничена зависимостями: в локальной копии `hash.h` убраны неиспользуемые Hash9/sha3/scrypt и их includes; SHA256/RIPEMD160/HMAC остаются исходными OpenSSL-вызовами. Добавлен явно управляемый test hook HMAC для10 граничных случаев; во всех остальных случаях он пуст и исполняется настоящий HMAC. Для неиспользуемого здесь перегруженного оператора BigInt добавлен compile define `BN_LONG=long`. Полный diff — артефакт исходного исследования (`native/hash.patch`; вне снимка), pins — артефакт исходного исследования (`native/INPUT_PINS.json`; вне снимка), команда/версии — артефакт исходного исследования (`runs/native-8f30656acce7/build.json`; вне снимка), вход — артефакт исходного исследования (`runs/native-8f30656acce7/inputs.json`; вне снимка) и сырой вывод — артефакт исходного исследования (`runs/native-8f30656acce7/stdout.txt`; вне снимка) сохранены.

**Это исполнение криптографического ядра с описанным адаптированным заголовком, не сборка исторического Qt/ODB-приложения и не воспроизведение OpenSSL2014.** Ошибка хранения `Keychain::child` первого захода принадлежит CoinDB и этим native harness не исполняется. В первой работе оставалось ограничение только Python-модели; теперь оно снято для проверенных функций CoinCore, но не для всех GUI/export/database операций.

Все308 случаев прошли:12 узлов BIP32 vectors1/2,256 synthetic children с сопоставлением уже сохранённым результатам,16 public/private проверок,10 injected IL,5 leading-zero parents, imported33-byte constructor, hardened-public rejection, неизвестная version,3 недопустимых пути и3 path aliases. Числа автоматически собраны в [NUMERIC_REPORT.md](<NUMERIC_REPORT.md>). Сборка2.955с, бинарный набор1.136с; это не время восстановления ключа.

Новые конкретные наблюдения:

- `HDKeychain(33-byte 00||private, chaincode)` отвергает такой аргумент как неправильную public point, тогда как78-byte xprv-конструктор работает. Это подтверждает оговорку первого захода для imported33-byte API: подобная путаница ломает вызов, а не обнуляет или сужает secret. Штатный CoinDB signing/export явно удаляет лишний00; отсутствие такого удаления в отдельном API не становится генератором малых ключей.
- Строковый parser принимает `/2` как `0/2`, одиночный апостроф как `0'`, `00/02` как `0/2`; `m/2/0`, `2/` и `2147483648` отвергает. Это воспроизводимые aliases пути. После выбора canonical path обычный HMAC сохраняется; дополнительные переборы вариантов одинакового пути смысла не имеют.
- Неизвестная version сохраняется при78-byte импорте, а getPublic выставляет default public version. Изменение заголовка не создаёт новый scalar/chaincode. Ведущие нули и исключения на invalid IL проверены уже в C++.

## История: что действительно менялось

GitHub API проверен для двух имён файла: `deps/CoinCore/src/hdkeys.cpp` и `deps/CoinClasses/src/hdkeys.cpp`, с ограничением истории предком cutoff commit. Получены3 записи по новому имени и10 по старому (переименование14.04.2014 присутствует в обоих списках); сохранены12 существующих редакций файла. В старом пути переименовывающий commit не скачивался, потому что файл уже перемещён. Самая ранняя просмотренная редакция — [8e1f287d от29.12.2013](https://github.com/ciphrex/mSIGNA/blob/8e1f287d7bd1d6e245f6f82047f9add5c1023772/deps/CoinClasses/src/hdkeys.cpp). Это граница наблюдаемого включения CoinClasses в этот репозиторий, не утверждение о всей более ранней upstream-истории BIP32.

Во всех12 редакциях private transition использует `k += Il`, затем modulo n; HMAC получает parent chaincode и33-byte key material + BE32 index; новый chaincode — IR. Включение исходников в декабре2013 уже после изменения стандарта на сложение. Связи Armory-типа с публично вычисляемыми множителями здесь не обнаружено.

Выявлено реальное отличие по invalid child: до [5881cff0 от03.03.2014](https://github.com/ciphrex/mSIGNA/blob/5881cff053e5ec5f65d67ea61507847a4d18ff83/deps/CoinClasses/src/hdkeys.cpp) возвращался invalid объект; с этого изменения выбрасывается исключение. Legacy `CoinQ::Keychain::numkeys` всё ещё имеет `if (!child) continue`, то есть логика skip рассчитана на старый контракт. В срезе2015 исключение до этого условия не позволяет skip. Эта несовместимость объясняет изменение поведения редкой ошибки, но не дешёвый root. При стандартном предположении равномерного HMAC даже верхняя BIP32-оценка для256 детей меньше2^-119; её нельзя превращать в предположение о сотнях пропущенных индексов.

Другие просмотренные изменения: проверка public point в конструкторе, copy constructor, namespace/include переименования, full_hash identity, строковые paths и uncompressed public output. Исторические метаданные и признаки переходов сохранены в HISTORY_FACTS.json — артефакт исходного исследования (`HISTORY_FACTS.json`; вне снимка). Полную native-проверку каждой старой редакции мы не заявляем: native исполнен cutoff-код, история сравнена по исходникам.

## Legacy CoinQ — другой экспорт, то же математическое семейство

В том же дереве остался CoinQ_vault_db.hxx — артефакт исходного исследования (`sources/deps/CoinQ/src/CoinQ_vault_db.hxx`; вне снимка), отличающийся от CoinDB Schema первого захода. `Key` берёт `extendedkey_->hdkeychain().getChild(childnum)`, а private-key getter проходит тот же index от private extended key. Сохраняется один xpub/xprv, а счётчик выдаёт прямых children0,1,…; это другая организация пула, но стандартная CKD. `Keychain::child` выводит публичный child от публичного parent — приватная ветка с ошибочным присваиванием из нового CoinDB сюда не переносится.

Важно различать создание: CLI-пример называет себя `CoinVault v0.0.1`, его `newkeychain <file> <name> <numkeys>` вызывает **независимое создание ключей** через CoinKey.generateNewKey; отдельного `newHDKeychain` CLI-command в просмотренном command map нет. HD поддерживается через библиотечный newHDKeychain и импорт уже готового extended-key файла. Нельзя объявить этот `newkeychain` удобным получением сотен связанных children без предварительного HD-импорта. Дата поставки данного примера в конкретном GUI-установщике не установлена.

Legacy deterministic export имеет123 байта:

```text
deterministic=01 | extkey_size=BE32(78) | extkey78 |
numsavedkeys=BE32 | hash_size=BE32(32) | SHA256d(public_extkey78)
```

Для public export весь файл позволяет восстановить xpub. Это **не Boost text archive** из первого захода. Для private export extended key содержит private данные, а hash всё равно вычисляется по public extended key. Недетерминированный формат вместо этого хранит private/public flag, список независимых ключей и цепочку хешей. Не нужно принимать все файлы `.pub`/`.priv` за один формат.

Новая полезная деталь: legacy identity связывает **все78 байт xpub**, включая version/depth/fingerprint/index. CoinDB identity связывает только pubkey||chaincode. Поэтому одинаковая криптографическая пара с разной metadata может иметь разную legacy identity. Ещё важнее: `numsavedkeys` не включён в hash; десять изменений счётчика прошли проверку неизменного хеша. Счётчик нельзя считать аутентифицированным доказательством количества детей или точного соответствия Puzzle. Проверка checksum вообще не доказывает происхождение артефакта от автора.

Сделан read-only legacy_profile.py — артефакт исходного исследования (`legacy_profile.py`; вне снимка), принимающий **только public deterministic123-byte export**. Он проверяет формат, point, xpub version и SHA256d, выдаёт обе identities и предупреждает в данных об отсутствии связи счётчика с hash.4 synthetic export cases,6 повреждений и10 замен счётчика прошли; исходный ODB-exporter при этом не запускался. Артефакты контроля — артефакт исходного исследования (`runs/legacy-a676fc1e0a81/results.json`; вне снимка). Все private/xprv в native-входах — synthetic либо опубликованные BIP32 test vectors, реальных кошельков пользователя не читали.

## Математический итог и точная граница

Новый альтернативный путь не даёт известных из Puzzle коэффициентов: и legacy прямые children, и CoinDB root/bin/i требуют неизвестных K/c внутри HMAC. Счётчики, identity и aliases не заменяют chaincode. Совпадение криптографической пары при разной metadata лишь повторяет тот же raw. Ни гипотезы короткого seed, ни ослабленного RNG здесь не использованы.

Новых реальных xpub-кандидатов0, восстановлений0, алгоритма с остатком≤2^32 нет. Это более сильная проверка реализации и исторической границы, а не повтор ранее заявленного generic BIP32 recovery. Из83 решений повторно использована только закреплённая копия/хэш; их полный EC-контроль первого захода не пересчитывался. Полные raw из synthetic native-inputs не выдаются за допустимый вход recovery: восстановления вообще не выполнялось.

Следующий содержательный эксперимент требует **новой связи или конкретного настоящего артефакта**, например legacy123-byte public export либо CoinDB root/bin export, с происхождением и индексами. Для первого теперь готов parser. Дальше расширять пустое дерево путей или просто удлинять перебор этот результат не обосновывает. Ни кошелёк целиком, ни все возможные атаки не объявлены исключёнными.
