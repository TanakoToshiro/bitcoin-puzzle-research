# Точная совместная модель и предел проверенного метода

Для old Electrum 1.7.4/1.9/1.9.8:

```
seed0 = ASCII(hex-seed), как хранит old wallet
h0 = seed0
h(t+1) = SHA256(h(t) || seed0), t = 0..99999
s = BE(h100000)
M = ser32(x(sG)) || ser32(y(sG))
z(c,k) = BE(SHA256(SHA256(ASCII(decimal(k)+":"+decimal(c)+":") || M)))
a(c,k) = z(c,k) mod n
raw(c,k) = (s + a(c,k)) mod n
r_i = d_i mod 2^(i-1)
```

Нет chaincode; c=0 receiving, c=1 change. MPK имеет 64 байта x||y без
SEC-префикса 04; raw pubkey/WIF — uncompressed. Целевой Puzzle в snapshot
использует compressed public/address: внешний скрипт должен заново кодировать ключ.
Счётчики — десятичные ASCII без leading zeros, не ser32(index). Последовательность
независимо индексируемая, предыдущий private child не является входом следующего.
В выбранном OldAccount отсутствует цикл пропуска нулевого raw child / бесконечной
точки. Для s вне допустимого диапазона проверку делает ecdsa SigningKey;
не приписываем исходнику несуществующий retry/modulo при создании master.
Наши синтетические s берутся из [1,n); это контроль деривации, не утверждение
о нахождении seed-preimage каждого выбранного s.

## Что меняют accounts и экспорт

Для CSV 1.9.8 без импортов и с одним old account:
`(c,k)=(0,i-1)` при i<=R, иначе `(1,i-R-1)` до i=R+C.
При I импортированных строках вместо i используется i-I; первые I не принадлежат
детерминированной цепочке. Каждый реальный переход по границе ветви меняет
вход SHA. Это небольшое семейство кусочных отображений при известном/ограниченном R,
но **не источник известного MPK**. Для обычного неиспользованного пула C=3.
Варианты C>3 требуют истории использования или явной дополнительной генерации.

Для 1.7.4 CSV через dict.items(): отображение зависит от словаря raw-адресов и
реализации Python 2. Свободные перестановки не перебирались. Известный runtime
не превращает неизвестные raw-адреса в известный порядок. Это дополнительная
неизвестная, а не криптографическое преимущество. Сохранённый исходный CSV
содержал бы сами полные raw private keys; оставшийся только преобразованный
список не сохраняет автоматически эту информацию.

## Совместное уравнение без MPK

```
M = ser64(sG)
s + a_i(M) - t_i*n = r_i + 2^b_i*q_i
t_i in {0,1}, 0 <= r_i+2^b_i*q_i < n, b_i=i-1
```

Разность двух строк убирает s, но оставляет `a_i(ser64(sG))-a_j(ser64(sG))`.
Определение M=sG уменьшает независимое число неизвестных (MPK не произвольные
512 бит), однако не даёт вычислить SHA offsets по младшим битам s. Нельзя
подменить a_i свободными целыми, а затем объявить найденный корень кошельком.
HNP-коэффициенты из Armory здесь не возникают: коэффициент s у всех детей равен 1,
а зависимость offsets от s проходит через полную точку и SHA256d.

Проверен конкретный точный baseline: перечислять s, вычислить M=sG, проверить
сначала самое длинное наблюдение; несовпавшие отбрасывать, остальные проверить
по всем наблюдениям. При последовательном диапазоне достаточно начального
scalar multiplication и по одному group addition на следующий M. Это сокращает
цену EC-операций на кандидата, но не число кандидатов. Каждый обычно требует
одного SHA256d, то есть двух SHA256 (не одной операции EC и не одного SHA).

Полный цикл по скалярам имеет n-1≈2^256 кандидатов, O(1) дополнительной памяти
помимо наблюдений/ответов. Если отдельно использовать образ штатного 128-битного
seed, исчерпывающий поиск имеет примерно 2^128 seed и 100000 SHA256 на stretch;
это другая стратегия, она не запускалась и не является слабым seed. Ни одна
оценка не является нижней границей всех возможных атак.
Исчерпывающие toy контроли порядка199 показывают точность системы и уникальность
8 положительных ответов, но всё равно перебирают все198 s. Это демонстрация
разницы между единственностью и стоимостью, не доказательство SHA-стойкости.
Полноразмерный pilot проверяет1024 s в **заранее сообщённом искусственном интервале**;
получить такой интервал из решений Puzzle метод не умеет.

## Когда найден настоящий артефакт

`old(MPK,branch,index)` в unsigned.txn устраняет неизвестный M и даёт один
якорь исходного child. Сам MPK проверяется как точка кривой; исходные address
и redeemPubkey, если есть, проверяются публичной деривацией. Это связывает
metadata внутри артефакта, но связь с Puzzle требует отдельной проверки.

Для заданного отображения индексов вычисляются a_i. Точные интервальные
условия по s реализованы в model.intervals, с выколотыми точками raw_i=0.
Непустое арифметическое пересечение **не доказывает** sG=MPK и не восстанавливает s.
Условная формула E7 для меньшей цели остаётся:

```
d_i in {2^b_i + ((r_j+a_i-a_j+u*n) mod 2^b_i): u=-1,0,1}, j>=i
```

Для C разных кандидатных MPK и L **обоснованных** отображений проверка
подготовленных offsets требует до C*L*m SHA256d; точное пересечение в этой
простой реализации O(m^2) модульных проверок и O(m) памяти. Из-за выколотых
нулей не более2m+1 отрезков. Для одной цели — до3 кандидатов/address проверок
на прошедшую пару. Сначала полезно отсеять неверные MPK четырьмя длинными
наблюдениями, потом сверить оставшиеся. Ни C, ни L не назначаются маленькими
без реального файла/источника и данных о порядке. В данном проходе новых
реальных артефактов0, реальных кандидатов MPK0.

Неизвестный полный raw child отличается от masked: при известных M,c,k полный
raw немедленно даёт s=(raw-a) mod n с проверкой sG=M. Masked key этого не даёт.
Даже полученный stretched exponent не означает обращение100000 SHA256 к mnemonic.
Новые реальные приватные ключи/биты не получены; бюджет порядка2^32 из доступных
данных не достигнут. Не найден способ убрать SHA-барьер; невозможность не доказана.
