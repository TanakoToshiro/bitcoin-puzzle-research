# EL-02 — Electrum: завершённый ограниченный этап

2026-11-02. **Без заранее доступного MPK нового практического восстановления
master или masked children не получено.** Новые результаты — подтверждённое
различие порядка экспорта между1.7.4 и1.9.8 и конкретный формат сопутствующего
артефакта с MPK: незавершённая транзакция `.txn` с `input_info.KeyID`.
Артефакт автора Puzzle не найден; положительные recovery-проверки только synthetic.
Electrum как возможный генератор не исключён.

## Исторические срезы и пользовательский путь

Основной: [1.9.8, f92b483942d3f8ee51506e0436d9b524db33a336](https://github.com/spesmilo/electrum/tree/f92b483942d3f8ee51506e0436d9b524db33a336), 16.03.2014 по принятому HD-01 pin.
Дополнительно выбран1.7.4, поскольку release notes1.7 описывают массовый экспорт
и Python console, а1.7.3 — account selector. Это позволяет проверить, означает
ли старый account selector новые детерминированные корни.
Тег1.7.4 указывает на `e8ffe29554dbb616005218f9686a3d9d8c85ca49`, commit14.05.2013.
Промежуточный1.9: `051c882a3f5288b467fbee1950ec391204a245c4`, tag04.11.2013.
Даты/объекты GitHub сохранены в SOURCES. Проверка ограничена этими срезами,
полная история всех pre-2015 сборок не заявляется.

Для нового обычного1.9.8 wallet без config.bip32 выбирается old seed_version4.
Путь: создать кошелёк → Python console `wallet.change_gap_limit(256)` →
`wallet.synchronize()` → Wallet / Private Keys / Export → CSV. В чистом
неиспользованном old account это256 receiving плюс3 change, всего259 строк
данных и заголовок. Генерация/synchronize нужна: изменение настройки само
по себе не создаёт строки. Существующая история может увеличить пул сверх
gap limit. Для desired256 ключей внешний скрипт может взять первые256
receiving; это должно быть явно задано.

Путь подтверждён исходниками и исполнением выделенных методов с подставными
account/storage/network объектами. Полный Python2/PyQt4 GUI не запускался;
скорость настоящего исторического GUI не измерена. В1.9.8 old private export
повторяет stretch/check-seed на строках, поэтому "удобный" не означает мгновенный.
Опция BIP32 существует, но не должна смешиваться с old-схемой по умолчанию.

## Что новое в порядке экспорта

| Путь | Фактическая последовательность | Что разрешено предположить |
|---|---|---|
| 1.9.8 CSV | Заголовок address/private_key; затем addresses(True), непосредственно в цикле | Для чистого old account — receiving0..R−1, затем change0..C−1 |
| 1.9.8 dumpprivkeys() | Тот же addresses(True), результат — список списков WIF | Это не плоский список и не словарь |
| 1.9.8 dumpprivkeys(addresses) | Порядок переданного списка | Любой иной порядок должен происходить из известного списка, не угадываться |
| 1.7.4 CSV | get_private_keys(...).items() | Python2 dict iteration; порядок деривации не гарантирован |
| 1.7.4 dumpprivkeys() | Словарь address→WIF | Не переносить list-семантику1.9.8 назад |

Доказательства: [CSV1.7.4:1757](https://github.com/spesmilo/electrum/blob/e8ffe29554dbb616005218f9686a3d9d8c85ca49/gui/gui_classic.py#L1757),
[CSV1.9.8:1954](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/gui/qt/main_window.py#L1954),
[addresses:538](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/lib/wallet.py#L538),
[get_account_addresses:1037](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/lib/wallet.py#L1037).

Imported keys идут префиксом addresses(); внутри их Python2 словаря порядок
не предполагается известным. Затем идут account-блоки в порядке keys() словаря,
внутри каждого сначала receiving, затем change. После них — ещё не включённые
адреса next_addresses. В NewWallet они соответствуют `(branch,index)=(0,0)`
следующего account; это не очередной child текущего account. Уже встреченный
адрес не добавляется второй раз. pending_accounts хранит metadata, а в экспорт
адрес попадает через next_addresses.

**Обычный OldWallet создаёт только account0.** В1.7.4 sequences[0] и штатная
инициализация также не дают набора независимых old accounts. Account selector
сам по себе не доказывает новые master keys. В1.9 old account определяется
seed_version4; в1.9.8 выделен класс OldWallet. Проверенные48 offsets трёх версий
совпали побайтно. Нового множителя/account salt в old-формуле нет.

Простой обоснованный map1.9.8 — кусочный receiving/change с границей R и
префиксом I импортов, см. [MATH.md](<MATH.md>). Нет основания объявлять
штатным export stride2, чередование receiving/change или reverse.
В1.7.4 dict-order зависит от исходных адресов и Python runtime; произвольный
перебор перестановок не выполнялся. Старые501 MPK и48 моделей№256 не повторялись.

CSV не содержит MPK, branch, index, label или account ID. Он содержит raw
address и WIF; если сохранён сам исходный CSV, полные raw keys уже доступны.
Не следует приписывать сохранившемуся только обработанному списку его metadata.
Несколько private WIF для multisig1.9.8 GUI склеивает через пустую строку:
это ещё одна причина не считать любую строку одним old child.

## Новый проверяемый профиль артефакта

Цепочка кода1.9.8:

1. `wallet.get_keyID(0,(c,k))` → `old(MPK,c,k)`.
2. `wallet.add_input_info` добавляет KeyID и исходный redeemPubkey ко входу.
3. `Transaction.get_input_info` копирует KeyID в metadata.
4. `Transaction.as_dict` включает input_info **только если is_complete=False**.
5. `TxDialog.save` пишет этот JSON в `unsigned.txn`.

Источники: [get_keyID:633](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/lib/wallet.py#L633),
[get_input_info/as_dict:669](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/lib/transaction.py#L669),
[save:108](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/gui/qt/transaction_dialog.py#L108).

`input_info` здесь JSON-строка внутри внешнего JSON, а не обязательно массив.
Один old KeyID даёт128 hex символов MPK, branch и index одного raw child.
Пример формы и готовый public-input verifier — [ARTIFACT_PROFILE.md](<ARTIFACT_PROFILE.md>).
При нескольких входах одного кошелька MPK повторяется и дедуплицируется.
Подписанный complete `.txn` по этому пути и обычная broadcast/raw blockchain
transaction не сохраняют эту metadata. Не утверждаем утечку MPK в блокчейн.

Это **новый целевой тип файла относительно рассмотренного E8 текстового
поиска**, а не обнаруженный файл создателя. Связанные с автором новые вложения
сейчас не известны; повторный общий веб-поиск не делался. Известный E8 scanner
непрерывных hex, вероятно, увидел бы MPK и внутри plain-text KeyID, если такой
документ уже был в его корпусе; здесь не заявляется обход прежнего поиска.

Другие пригодные артефакты: old wallet/watch-only backup с top-level
`master_public_key`, скопированный getmpk или GUI MPK/QR. В1.9.8 OldAccount.dump
не дублирует mpk в accounts[0]; нужен верхний уровень wallet storage.
Обычная адресная строка, label-export и txid этим профилем не являются.
Для1.9.8 BIP32 getmpk возвращает repr((chaincode,K)), а не обязательно xpub
Base58; metadata надо разбирать по версии. См. CROSS_FINDINGS.md.

## Вычисления и честный предел

Все числа строятся из сохранённых результатов: [NUMERIC_REPORT.md](<NUMERIC_REPORT.md>).

- 83 входных ключа независимо сверены по диапазону, secp256k1 public и P2PKH;
  SHA256 snapshot совпал с HD-01, максимум134 младших бита, сумма3767.
- 6 source fixtures подтверждают порядок/пул/dump/metadata;48 offsets совпали
  у1.7.4,1.9,1.9.8. Python2 dict hash-order не эмулировался.
- На малой настоящей EC порядка199 проверены8 положительных и8 отрицательных
  точных совместных EC+SHA256d систем. Решатель не получает MPK или secret.
  Каждый исчерпывающе проверяет198 s; результаты совпали с отдельным полным
  oracle, считающим каждую точку заново. Восемь уникальных положительных решений,
  восемь несовместных отрицательных. Offsets нигде не заменены свободными числами.
- 4 synthetic секp256k1-sized exponents, receiving-count256/132/100/70:
  отдельный процесс разбирает KeyID, сверяет raw anchor и4 masked наблюдения,
  выдаёт три кандидата№71; адрес оставляет правильный во всех4 случаях.
  Оставшиеся79 реальных по форме масок/пропусков на случай проверены после
  вывода, всего316 проверок;12 отрицательных изменений отклонены/не дают ответа.
  Формула трёх переносов уже была в E7; новое здесь — интерфейс артефакта и
  кусочные export maps, включая смену ветви между наблюдением и целью.
- Full-size joint pilot:1024 скаляра в заранее заданном synthetic интервале;
 1106 SHA256d в положительном и1024 в отрицательном контроле. Интервал не
  выведен из Puzzle. Это работоспособный verifier, не восстановление256 бит.

Полная постановка и стоимость — [MATH.md](<MATH.md>). Удаление s вычитанием
уравнений оставляет неизвестные SHA256d от ser64(sG). Ни порядок экспорта,
ни old accounts не дали способа вычислить эти offsets без MPK. Прямой точный
перебор s остаётся порядка2^256; пространство штатных128-битных seed отдельно
меньше, но его исчерпывающий поиск не практичен и здесь не запускался.
Это оценки конкретных методов, не доказанные нижние границы криптоанализа.
Практического пути порядка2^32 из83 решений и исходников не получено.

## Что дальше

Содержательный следующий вход — связанный с автором unsigned/partially signed
Electrum `.txn`, old watch-only backup либо MPK с происхождением. Затем:
проверить точку и raw anchor; ограничить export map по реальным размерам пула;
проверить4 длинных наблюдения,79 оставшихся и целевой адрес. Сейчас число
новых реальных MPK-кандидатов0, новых приватных ключей/битов0. Отсутствие
такого артефакта не доказано глобально; стадия завершена ограниченным результатом.

Все записи только в02-electrum. Общие RESULTS/README, чужие эксперименты,
окружения и GPU-процессы не изменялись. Synthetic secret — контрольный скаляр,
не реальные средства и не найденный mnemonic. Источники, ошибки DNS,
UTC/SHA256, коды и public-input результаты сохранены.
