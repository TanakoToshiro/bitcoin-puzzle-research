> Исполняемый код/команды опущены в документационной копии.


Первые две команды используют content-addressed run ID. Если COMPLETE.json
уже есть, возвращают сохранённый результат и не повторяют вычисления.
Проверка целостности выполняется `seal.py`. При изменении существенных входов
создаётся другой run ID; старые completed и failed runs сохраняются.
Java subprocess limits: compile/JUnit 60 s, harness 120 s; Python controls
целиком 120 s, отдельный predictor 60 s. Окна приложений не открываются,
сеть во время контролей не используется.

При другой установке JDK изменить путь JDK в `run_java.py` перед новым запуском
и сохранить его в provenance. `build_report.py` пересобирает только числовой
отчёт и source facts из имеющихся JSON; RESULTS.md содержит интерпретацию.

## Источники и возобновление

HTTP-метаданные, ошибки первоначального sandbox DNS, успешные загрузки с
разрешённым network access и хэши сохранены в SOURCES.json. Для скачивания
исходников есть конечные manifests `metadata_urls.json`, `source_urls.json`,
`dependency_urls.json`, `additional_urls.json`; `fetch_sources.py` проверяет
кэш и не скачивает успешные источники заново. Дополнительная копия BIP32
исторического текста имеет provenance общего HD-01 snapshot.

`prepare_sources.py` предназначен для первоначального копирования общих входов,
а не для замены замороженного snapshot новым состоянием. При новом исследовании
сохранять новые входы/протокол отдельно. Общие лабораторные файлы и соседние
эксперименты не изменять.

Этап завершён. Что неизвестно: реальный account xpub автора, точная программа,
порядок экспорта и выбор старого migration key. Для продолжения нужен конкретный
относящийся к автору артефакт либо новый конечный алгоритм неизвестного xpub.
