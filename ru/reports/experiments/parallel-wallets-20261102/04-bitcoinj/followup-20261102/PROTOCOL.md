# B4-R2 — второй анализ приложения и ключей

Запрошен пользователем 02.11.2026 после завершения B4. Первый этап и его
completed runs сохраняются. Все новые файлы — в этой подпапке задания №4.
Подагенты, GPU, облако, пакеты общего venv и соседние эксперименты не используются.

## Новые вопросы

1. Изменили ли bitcoinj 0.12.1/0.12.2 до 15.01.2015 HD-формулу, хранилище,
   экспорт и связи старой/новой chain при rotation? Закрепить commits и
   соответствующие Android 4.07/4.11/4.15/4.16 source tags.
2. Несут ли encrypted protobuf/cached seed и clone/restore структуру,
   раскрывающую public anchor или private bytes без предположения слабого RNG
   либо перебора PIN/паролей? Проверять исполнением release JAR, разделять
   внутреннее шифрование секретов и внешнее шифрование Android backup.
3. Меняет ли восстановление старого текстового backup выбор migration origin?
   Сначала точный caller/source, затем конечный контроль timestamp/order.
4. Если lifecycle повторно выдаёт один и тот же raw child, его masked копии
   обязаны совпадать по общим младшим битам. Проверить это необходимое условие
   для всех пар фиксированных 83 решений, с положительными/отрицательными
   малыми и полноразмерными synthetic controls. Это проверка конкретной
   reuse-модели приложения, не поиск корреляций HASH160.

## Бюджет до вычислений

- HTTP: конечные manifests, 25 s/попытка, максимум 2 попытки на URL.
- Java: compile до 60 s, один bounded harness до 90 s на версию,
  максимум 5000 children на версию, heap 512 MiB; никаких сетевых соединений.
- Проверка reuse: максимум C(83,2)=3403 пар, CPU, до 60 s.
- Малые точные модели: не более 65536 scalar-состояний на модель, до 60 s.
- Новый solver, если он обоснован исходниками: сначала отдельный PROTOCOL
  addendum с конечной ценой; полноразмерный seed/chaincode brute force запрещён.
- Успешные downloads и completed runs с теми же хэшами не повторять.

### Addendum до нового lock-пробника

После 90 s timeout на auto-upgrade 0.12.1 найден вызов upgrade(write lock)
из currentKey(read lock). Отдельный AutoUpgradeProbe ограничен 15 s с внутренним
JVM watchdog после 2 s и записью thread stacks. Остальные lifecycle-сценарии
используют явный public upgrade до currentKey; это разрешённый documented API.
Внешний jstack не используется после ошибки attach; runner всегда завершает
свой child в finally. Timeout сам по себе не считается доказательством проблемы.

## Входы/критерии

Замороженный snapshot SHA-256
`d291351169b1bb483b580af8cf4c30e503941f7b15b81aabd418e93809a40b70`.
Первая проверка диапазонов/public/address принята из B4; подтвердить хэш.
Реальные keys — окончательные Puzzle keys; raw observations — только i−1
младших битов, forced MSB не используется. Raw/public seed synthetic control
не передавать предполагаемому public-input анализатору.

Результат — новые подтверждённые app-specific связи либо точное ограниченное
сведение. Не объявлять 0.12.2/rotation исследованными по одному сходству README.
Не повторять общий HD-01 известного xpub; первого восстановления из одних
решений без дополнительного артефакта не обещать.
