# A1: откуда берутся коэффициенты и что остаётся неизвестным

Порядок n — secp256k1; U(P)=04||X_BE32||Y_BE32, D=SHA256∘SHA256.
Armory root имеет chainIndex=-1; первый child — 0. Для отдельной гипотезы
экспорта ниже puzzle i соответствует chainIndex i−1. Такое соответствие
не установлено для автора и должно входить в пакет проверки явно.

```
u_j = BE(C XOR D(U(P_j)))        # 0 <= u_j < 2^256, полный log multiplier
m_j = u_j mod n
k_(j+1) = m_j*k_j mod n
P_(j+1) = m_j*P_j
observed_i = 2^b_i + (k_j mod 2^b_i), b_i=i−1
```

В private/public переходах chaincode неизменен. Штатный wrapper пересчитывает
результат дважды, при расхождении трижды; это проверка согласованности вычислений,
а не BIP32-повтор индекса при недопустимом child. Явного skip нулевого scalar
в просмотренном C++ нет. Наш решатель отвергает m=0 и точку бесконечности;
в контролях они не встретились. Это точное ограничение домена реализации.

По умолчанию C=g(root): двойной SHA256 от BE32(root), затем историческая
HMAC256 с 32-byte pads и строкой `Derive Chaincode from Root Key`.
Это не стандартный HMAC-SHA256 с 64-byte блоком. Переданный явно C допускается.
Для default нельзя считать root и C независимыми 512 битами.

## Новый вход: log вместо watch-only

Для связанного упорядоченного сегмента журнала от anchor a известны u_j,
следовательно A_t=∏_{j=a}^{t−1}m_j mod n и k_t=A_t*s mod n, s=k_a.
Для наблюдения r_i=k_t mod 2^b_i:

```
alpha_i = A_t * inverse(2^b_i,n) mod n
beta_i  = r_i * inverse(2^b_i,n) mod n
alpha_i*s - beta_i = q_i (mod n)
0 <= q_i <= floor((n-1-r_i)/2^b_i)
```

Коэффициенты получены из конкретных строк журнала, а не приняты свободными.
Применяется та же 5-мерная HNP-решётка HD-01 для четырёх масок; LLL/Babai
не претендует на гарантированную полноту. Сохранены B, U, U·B, цель и ответ;
проверены det(U)=±1 и U·B=B_reduced.

После получения s вычисляем P_a=sG и
`C=BE32(u_a) XOR D(U(P_a))`. В журнале u_a до mod n, поэтому нет развилки m+n.
Далее заново строим всю цепочку: проверяем каждый HASH160(U(P_j)), каждый
u_j и одинаковый C. Неверный ближайший вектор не объявляется решением.
Первые четыре маски участвуют в подборе; остальные достижимые известные
индексы и новые synthetic цели проверяются только после восстановления.

Восстановлен root только при a=-1. При a>=0 получен полный scalar дочернего
якоря и C; можно идти вперёд. Без публичных точек предшественников либо
предыдущих множителей обратный переход здесь не построен. Даже default
C=g(root) после получения C не даёт обратимого g.

Если вместо журнала известны (P_a,C), A_t вычисляются публичной деривацией.
Это проверенное расширение интерфейса HD-01 на дочернюю запись, не новая HNP.

## Неизвестный C с двумя исходными точками

Если известны именно P=kG и младшие b бит r исходного scalar, то
`P-rG=q*(2^b G)` при `Q=floor((n-1-r)/2^b)+1` возможных q.
BSGS решает за O(sqrt(Q)) EC операций и столько же записей; kangaroo может
экономить память, но здесь не запускался. Для двух соседних полных результатов:

```
m = k_next * inverse(k,n) mod n
u in {m,m+n}, u < 2^256
C = BE32(u) XOR D(U(P))
```

Полнота этой последней развилки следует из n>2^255. На маленькой группе
проверены все q и все 256 возможных C. На secp256k1 успешно проверены два
контроля с **b=240**, то есть существенно большей утечкой, чем в Puzzle.
Это проверка реализации и масштаба группы, а не практический recovery Puzzle.
При настоящих b<=134 запуск заранее запрещён бюджетом 4096 baby steps.

Максимальная соседняя пара известных решений в снимке — №69/70:
b=68/69, поэтому два DLP стоят порядка 2^94 и 2^93.5 EC операций, доминирует
2^94. Это условное улучшение относительно E6H 2^128 **за счёт дополнительных
private residues и исходных points**, но не достижение 2^32. Для одного №135
и известного raw P стоимость около 2^61; соседнего столь же длинного решённого
ключа нет, поэтому эту цифру нельзя объявить ценой восстановления C.

Публичная точка окончательного Puzzle key не является P. Для высоких нерешённых
номеров E6H строил небольшие множества условных raw points; это не раскрывает
численное r и не создаёт b=249..255 известных private bits. Объединять эти два
разных вида сведений в один interval-DLP без дополнительного основания нельзя.

## Почему решения сами по себе не дали HNP

Пусть h_j=D(U(P_j)). Даже если P_j условно известны, XOR можно записать как
`u_j(C)=h_j + sum_l (1-2*h_j,l)*2^l*C_l`, где C_l∈{0,1}.
При k_j=r_j+2^b_j*q_j произведение k_j*u_j(C) содержит q_j*C_l и неизвестные
переносы modulo n. Это уже не HNP с известными A_i. Если P_j неизвестны,
h_j дополнительно зависит от полной EC-точки k_jG через SHA256.
Постоянство C даёт общую нелинейную систему, но её единственность не делает
поиск дешёвым. Default-связь C=g(root) сохраняет эту трудность.

Выполненная работа снимает требование заранее знать P_root и C **при наличии
другого исторически реального артефакта — multiplier log**. Только из 83
решений и кода коэффициенты не получены. Это предел проверенных методов,
не доказательство невозможности иных атак и не исключение Armory.
