# A1 — Armory classic, протокол до вычислений

Дата: 2026-11-02. Commit 61a596fa94f9cacf9fb00c4e02d0eb65d8b17513 (2015-01-08).
Только эта папка изменяется. CPU; без подагентов, GPU, перебора seed и feedback.

## Вопрос и отличие от HD-01/E6H

1. Установить реальные носители P, C, chainIndex: PKCC, сериализованная
   PyBtcAddress, watch-only wallet и обычный текстовый export. Реализовать строгую
   проверку PKCC/отдельной записи без запуска исторического GUI.
2. Проверить HNP от произвольного индексированного дочернего публичного якоря
   с C: корень и его публичная точка отсутствуют на входе; восстановить именно
   scalar якоря и только достижимые последующие ключи. Возможность ранее
   упомянута HD-01 как следующий шаг; новизна здесь — формат артефакта и проверка,
   не изобретение HNP. Реальные маски/пропуски 83 решений сохраняются.
3. Неизвестный C: два соседних raw public keys + частичные private observations
   дают два interval-DLP: Q=P-rG=q(2^bG), 0<=q<=floor((n-1-r)/2^b).
   После двух DLP C=(k_next/k mod n + t*n) XOR D(U(P)), t=0,1 при <2^256.
   Это частично использует старую инверсию полных ключей E3, но цена получения
   полных ключей из частичных явно измеряется и сравнивается с E6H.
   Без исходных точек DLP-входа нет. Для несоседних наблюдений формула C неверна.
4. Выписать совместную систему для неизвестных C и P, место нелинейности,
   профиль минимальных достаточных артефактов и границу применимости.

## Бюджет и приёмка

- Общий CPU-пилот <=180 секунд, каждая стадия <=60 секунд; подпроцессы с timeout.
- Полный малый контроль interval-DLP на реальной игрушечной EC порядка 199:
  все ненулевые scalars, b=1..7; неверные residues тоже проверяются.
- Совместная toy-задача: 16 пар, полный перебор 256 вариантов C для проверки
  полного множества, включая невозможные наблюдения и modulo-lift m+n.
- secp256k1: 6 дочерних якорей (несколько позиций и default/explicit C),
  четыре наблюдения 120/125/130/135; отдельный решатель видит только публичный
  пакет. Изменения C, residue, индекса, типа публичной точки отвергаются.
- Полноразмерный interval-DLP: 2 synthetic пары с явно усиленной утечкой b=240
  (16 неизвестных битов), не выдавать за реальные маски Puzzle. Реальные маски
  проверять аналитически и отказывать в запуске при >4096 baby steps.
- Проверить диапазоны/public/address всех 83 фиксированных решений и их SHA256.
- Сохранять inputs/outputs, времена, счётчики, версии, код каждого запуска.
  Завершённые стадии при resume не повторять; ошибки записывать отдельно.
- Неудача/непрактичная стоимость не исключает Armory и не доказывает нижнюю
  границу всех атак. Synthetic успех не является решением реального Puzzle.

## Дополнение до первого вычислительного запуска: штатный multiplier log

В safeExtendPrivateKey/safeExtendPublicKey обнаружена безусловная запись
`PrvChain (pkh, mult): HASH160,RAW_MULTIPLIER` (либо PubChain) в multipliers.txt.
Это новый конкретный источник коэффициентов, которого нет в условиях HD-01.
Приоритет: отдельный solver получает только упорядоченный сегмент этих строк,
его начальный chainIndex, четыре маски и отображение индексов. Ни P, ни C,
ни полные raw keys ему не передаются. HNP выдаёт scalar якоря; проверка HASH160
первой строки связывает ответ с журналом. Затем C=raw_multiplier XOR D(U(P))
и проверяются все строки, постоянство C и отложенные synthetic наблюдения.
Шесть positive и по четыре negative, anchors -1/0/59/70/114/119, включая
default/explicit C; восстановление root заявлять только при anchor=-1.
Необязательный широкий поиск публикаций не проводится. Требуется настоящий
журнал автора или связанный диагностический архив, которых в текущих входах нет.
Бюджет остаётся прежним; 2 новых стадийных пилота <=60 секунд каждый.
