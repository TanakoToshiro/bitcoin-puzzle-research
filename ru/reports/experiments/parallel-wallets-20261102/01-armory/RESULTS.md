# Задание №1 — Armory classic

**Получен новый условный synthetic recovery: штатный журнал `multipliers.txt`
позволяет восстановить приватный scalar и chaincode по четырём частичным
дочерним ключам, не зная заранее ни root public key, ни chaincode. Настоящего
журнала автора Puzzle у нас нет; нового реального ключа или сокращения поиска
только из опубликованных решений не получено.**

## Что добавлено к HD-01

HD-01 вычислял HNP-коэффициенты через известные (P_root,C). Здесь найден иной
конкретный исторический источник: при успешном private/public переходе Armory
дописывает HASH160 исходной несжатой публичной точки и **полный XOR-множитель**
в multipliers.txt. Запись находится в штатном wrapper, вне CRYPTO_DEBUG.
Проверены январский срез 61a596fa94f9cacf9fb00c4e02d0eb65d8b17513 и официальный
релиз v0.92.3, commit 268db0f3fa20c989057bd43343a43b2edbe89aeb от 02.10.2014.

Первичные источники релиза:
[private/public logging](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/armoryengine/PyBtcAddress.py#L423),
[полный multiplierOut](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/cppForSwig/EncryptionUtils.cpp#L753),
[имя журнала](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/armoryengine/ArmoryUtils.py#L407).

Произведения журналируемых множителей дают A_i в `raw_i=A_i*s mod n`.
Четыре наблюдения №120/125/130/135 дают HNP с b=119/124/129/134. После
восстановления s получаем P=sG и `C=u XOR doubleSHA256(U(P))`; проверяем
HASH160 и множитель каждой строки, затем отложенные ключи. Журнал содержит
u до mod n, поэтому здесь нет неопределённости между m и m+n.

В отдельном процессе получено 6/6 успехов log-only и отклонены 24/24
отрицательных пакета. Входы не содержат P, C, root private или полных raw
children. Использованы шесть позиций якоря (-1, 0, 59, 70, 114, 119), default
и explicit chaincodes, настоящие маски и пропуски 83-решённого снимка.
Это восстановление scalar якоря; **корень восстановлен только при anchor=-1**.
Поздний сегмент не даёт неизвестные предыдущие множители или обратный ход.
Синтетические цели №140/160 предсказаны и проверены вне четырёх обучающих масок;
№71 — только когда якорь не позже её позиции. Ни одна из них не является
новым реальным решением Puzzle.

Числа, точные времена, число holdout для каждого якоря, BSGS-счётчики и бюджеты
собраны из JSON в [NUMERIC_REPORT.md](<NUMERIC_REPORT.md>). Решётки и их
преобразования сохранены в SOLVER_OUTPUT.json активного запуска. Скорость
восстановления не включает получение отсутствующего журнала, установление
авторства, разделение смешанного журнала или поиск index mapping.

## Историческая достижимость и артефакты

Обе проверенные версии предусматривают GUI Extend Address Pool → сотни
адресов → Key Lists с Include Unused и private Hex/Base58. Сам старый GUI
не запускался; путь прослежен по исходникам. Это подтверждает возможность
сценария до 15.01.2015, не использование Armory автором Puzzle.

Журнал может оказаться также в диагностическом архиве: recovery копирует
его в папку, из которой GUI собирает ZIP. Это конкретное место для проверки
**если появится связанный с автором артефакт**, а не утверждение, что такой
архив уже найден или опубликован.
[Копирование](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/armoryengine/PyBtcWalletRecovery.py#L1715),
[архивирование](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/qtdialogs.py#L973).

Дополнительно разобраны PKCC, бинарная 237-byte запись дочернего адреса и
обычный текстовый export. C повторяется в дочерних бинарных записях; потому
для forward recovery достаточно одной записи (P_child,C,index), root record
необязателен. В отдельном процессе этот вариант дал 6/6 positive и 24/24
negative. Саму возможность раннего публичного якоря уже упоминал HD-01;
новое здесь — проверенный интерфейс, форматы, границы и контролируемые пакеты.
Обычные child-строки Export Key Lists C не содержат.

Готовые строгие parsers PKCC/record, смещения, checksums, минимальный
достаточный профиль и ограничения — [ARTIFACT_PROFILE.md](<ARTIFACT_PROFILE.md>).
Выбранные исторические log-методы исполнены без изменения тела с адаптером
данных/C++; historical serialize совпал побайтно. Это не запуск полного
старого приложения. Независимая affine-арифметика проверила 35 переходов.

## Неизвестный C без журнала

Проверен конкретный условный путь: исходные публичные точки двух соседних
детей + младшие private bits → два interval-DLP → полные scalars → один/два
C-кандидата. Малый контроль проверяет полноту перебором; полноразмерный
контроль реализован на secp256k1 с явно усиленной утечкой b=240. Он не
выдаётся за реальную Puzzle-маску; при b=134 решатель отказывает по бюджету.

В фиксированном снимке лучшая соседняя пара — №69/70. Оценка около 2^94 EC
операций с обязательными исходными точками существенно хуже практической
цели. Даже условные 2^61 для одного №135 не дают C без второго подходящего
звена. Это дополнительная информация по сравнению с E6H, где XOR-MITM
оставался около 2^128; одинаковыми условия этих задач не объявляются.

Без исходных точек и журнала коэффициенты зависят от неизвестного C и
SHA256 полных raw points. Совместные уравнения, билинейные члены XOR,
default-связь C=g(root), оценка времени/памяти и границы приведены в
[MATH.md](<MATH.md>). Публичные точки изменённых Puzzle keys не подставлялись
вместо raw points. Feedback, RNG-перебор и повтор XOR-MITM не запускались.

## Приёмка и следующий шаг

Все 83 решения повторно проверены по диапазонам, публичным ключам и адресам.
SHA256 снимка совпал с HD-01:
`d291351169b1bb483b580af8cf4c30e503941f7b15b81aabd418e93809a40b70`.
Неизвестные ключи не заменялись нулями. Завершённые стадии при resume не
пересчитываются. Ошибочный ранний запуск сохранён: сравнивался порядок,
а не множество двух XOR-кандидатов C; нормализация исправлена до принятой
серии. История — [JOURNAL.md](<JOURNAL.md>), команды — [README.md](<README.md>).

Следующий достаточный вход — multipliers.txt/диагностический архив автора с
проверяемой связью и порядком, либо PKCC/дочерняя запись с C и point. Пока
такого входа нет, дальнейший большой перебор этим результатом не обоснован.
Armory не исключён; невозможность иной атаки не доказана. Мировая новизна
HNP/LLL или атаки по известным множителям не заявляется.

Изменялась только папка 01-armory. Общие RESULTS/README, чужие эксперименты,
GPU-процессы и общая Python-среда не изменялись.
