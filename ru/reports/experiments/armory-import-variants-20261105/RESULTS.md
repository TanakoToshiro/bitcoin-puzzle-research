# ARM-IMP-01 — Armory: исторические версии и импорт

05.11.2026, Europe/Moscow. **Проверены дополнительные срезы и конкретные пути импорта. Практического восстановления из одних опубликованных решений Puzzle не получено; ограниченного слабого генератора для нового перебора не обнаружено. Armory не исключён.**

Это продолжение [A1](<../parallel-wallets-20261102/01-armory/RESULTS.md>) и [A1-R2](<../parallel-wallets-20261102/01-armory/round2-20261102/RESULTS.md>). Их синтетические recovery-результаты и manifests не менялись и не пересчитывались.

При явно заданных root и C все шесть маршрутов сохраняют оба значения. Начиная с проверенного 0.90, root-only восстановление вычисляет прежний нестандартный HMAC256 с 32-байтным размером дополнения; это не стандартный HMAC с блоком SHA256=64 байта. В 0.88 отсутствие C вызывает новый запрос случайных байтов. Поэтому **подставлять вычисленный из root chaincode вместо потерянного случайного C старого кошелька неправильно**.

Формула перехода во всех шести исходниках сохраняется: `k_next = k × (C XOR SHA256d(uncompressed(P))) mod n`. В C++ изменены обёртки, диагностика и вывод полного множителя, а не эта формула. Нового шестикратного множителя пространства по версиям при одинаковых root/C не возникло. C++ в этом этапе сопоставлялся по исходникам; новый полный native build не заявляется.

Извлечены также vendored Crypto++ osrng/randpool/rng из тех же архивов: RNG_SOURCES.json — артефакт исходного исследования (`RNG_SOURCES.json`; вне снимка). AutoSeeded RNG обращается к OS_GenerateRandomBlock; в соответствующих платформенных ветвях это CryptGenRandom или /dev/urandom. В X917 и seed, и AES key берутся из этих данных. В ранних срезах объект генератора статический, в более поздних создаётся заново, но короткого timestamp-only или 32-битного seed-пути здесь не найдено. Это анализ исходников, не аудит каждой ОС, сборки, ошибки entropy-провайдера или состояния машины автора.

Источники: [0.88 create/root и импорт](https://github.com/etotheipi/BitcoinArmory/blob/8af1b12eda3e3796c1318eef050c4899f43db1bf/armoryengine.py), [0.92.3 wallet](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/armoryengine/PyBtcWallet.py), [X917 auto-seeding](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/cppForSwig/cryptopp/osrng.h).

## Какие варианты импорта проверены исполнением

На CPython 2.7.9 Windows amd64 и Linux64 исполнены буквально выделенные исторические Python-методы. Реальные secp256k1-точки считала python-ecdsa 0.11; независимая Python3-проверка использовала отдельную аффинную арифметику. PyQt4/SWIG, диск wallet и blockchain заменены адаптерами. Трасса createNewWallet останавливается после выбора root/C, до создания файла; запросы RNG в этой трассе возвращают заданные синтетические байты. Это проверяет выбор маршрута и число запросов, а не качество CSPRNG.

| Путь | Результат |
|---|---|
| Raw hex, uppercase hex, обычный uncompressed WIF, raw с checksum | Возвращают один и тот же 32-байтный скаляр. |
| Ошибка одного байта в checksummed ключе | verifyChecksum исправляет её; в проверке восстановлен исходный ключ. |
| Байты raw перевёрнуты, checksum оставлен от исходных | verifyChecksum распознаёт reverse и возвращает правильный порядок. |
| Две повреждённые позиции | Контрольный пример отвергнут. Не заявляется отсутствие всех возможных checksum-коллизий. |
| Мини-ключи | Parser принимает 22 и 30 символов. Сам decodeMiniPrivateKey умеет также 26, но внешний parser их не пропускает. Вариант с marker=01/PBKDF2 не поддержан. |
| Compressed WIF | Parser может вернуть 38 байтов; фактический createFromPlainKeyData требует ровно 32 и отвергает их. Это не молчаливый успешный импорт с потерей compression-флага. Python с отключёнными assert не исследовался. |
| Raw ноль и n | Utility parser сам по себе возвращает байты; это не свидетельство, что допустим кошелёк с таким ключом. В одиночном GUI есть отдельная проверка диапазона. Полное поведение всех некорректных bulk-входов через native C++ не проверено. |
| Строка формы BIP38 | В проверенной точке входа декодера BIP38 нет; тестовый Base58-вход длины 58 с префиксом 6P отвергнут. SecurePrint — отдельный механизм, его не следует считать BIP38. |
| Одиночный GUI import | «Да» первому адресу передаёт исходные байты. «Нет», затем «Да» второму адресу передаёт byte-reversed scalar. «Отмена» не вызывает импорт. Тело метода исполнено до перехваченного вызова записи. |
| Engine importExternalAddressData | Два разных ключа добавлены, повтор первого не добавлен. Импорт получает chainIndex=-2, C=ff…ff; root/C кошелька не изменены. |

Compressed-key error detection немного различается: в 0.90 проверяется позиция marker перед checksum, в соседних рассмотренных версиях условие иное. Однако это не меняет установленного ограничения штатного 32-байтного конструктора для полного compressed WIF. Искусственно обрезанный или заранее преобразованный внешний ключ — иной сценарий, требующий собственных входных данных.

Одноимённый engine-метод `bulkImportAddresses` во всех выбранных срезах — незавершённая заглушка, возвращающая None. Реальный GUI-путь списка ключей находится в DlgImportAddress.processMultiSig: он проходит строки, пропускает PublicX/PublicY, дедуплицирует адреса и отдельно вызывает importExternalAddressData. Этот GUI bulk-путь просмотрен по исходникам; целиком со всеми диалогами и нативными ошибками не исполнялся. В частности, успешный вызов заглушки нельзя считать проверкой bulk-import.

Источники: [utility parser и checksum](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/armoryengine/ArmoryUtils.py), [конструктор адреса](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/armoryengine/PyBtcAddress.py#L366), [GUI-импорт](https://github.com/etotheipi/BitcoinArmory/blob/268db0f3fa20c989057bd43343a43b2edbe89aeb/qtdialogs.py#L3128).

## Порядок экспорта и последствия для Puzzle

GUI Key Lists берёт `getLinearAddrList(withAddrPool=True)` и сохраняет порядок записей кошелька, затем применяет фильтры. Это не список, отсортированный по chainIndex. Импорты могут оказаться между детерминированными записями, если после них расширяли пул.

Контрольная история `[0,1,2,importA,importB,3]` дала:

| Выбор | ChainIndex в выдаче |
|---|---|
| С unused-пулом | 0, 1, 2, −2, −2, 3 |
| Без unused при highestUsed=1 | 0, 1, −2, −2 |
| Без импортов, с пулом | 0, 1, 2, 3 |
| Только импортированные | −2, −2 |
| Отдельный sorted helper | −2, −2, 0, 1, 2, 3 — **не порядок GUI** |

Одинаковый результат получен на шести срезах и двух runtime-профилях. Значения всех экспортированных ключей и uncompressed-P2PKH адресов сверены независимо. В 0.88 hex отображается группами с пробелами; это отличие представления, не иной скаляр.

Импорт не превращает исходный ключ в deterministic root и не делает imported записи потомками root. Внешние ключи могут происходить из совершенно другого генератора. Если автор маскировал строки общего экспорта по номеру строки, число/место импортов и unused-пул влияют на mapping. Без исходного файла эти данные неизвестны; произвольный перебор перестановок не запускался.

## Остальные маршруты: что установлено по исходникам

| Маршрут | Что происходит и граница проверки |
|---|---|
| Полный Armory wallet-файл | Это загрузка имеющегося состояния/записей; меню выбирает *.wallet. Не доказан универсальный конвертер Bitcoin Core wallet.dat. Файловая миграция всех исторических форматов не исполнялась. |
| Старый paper/root+C | Восстанавливает оба явных значения. Imported ключей в root/C нет. Их необходимо сохранять отдельно. |
| Новый короткий paper/root-only | Получает C из root. Нельзя этим способом заменить отсутствующий random C кошелька 0.88. Формат выбирается также по сравнению сохранённого C с производным, а не только по номеру программы. |
| Fragmented backup | В просмотренном 0.92.3 реконструирует либо 64 байта root+C, либо 32 байта root с последующим выводом C. Полный Shamir/recovery GUI в этом этапе не повторялся. |
| SecurePrint | Предварительно снимает маску через отдельный KDF/unmask, затем использует те же root/C или imported key. Криптография маскирования и все варианты паролей в этом этапе не исполнялись. |

| Sweep | Переводит средства на выбранный адрес целевого кошелька; это не импорт новой deterministic цепочки из чужого private key. Создание/отправка транзакций не выполнялись. |

## Почему восстановление без дополнительных данных остаётся открытым

Предыдущие A1/A1-R2 решают задачи с известными множителями переходов или дополнительными публичными параметрами. Из одних опубликованных маскированных решений коэффициенты A неизвестны: они зависят от C и полных исходных публичных точек. Публичные точки самих уменьшенных puzzle-ключей не равны этим исходным точкам.

Новое уточнение ограничивает применимость журнала: **0.88/0.90 не пишут тот штатный multipliers.txt, на котором основан условный recovery A1**. Нельзя обещать найти такой файл в каждой старой установке. Для 0.91.1/0.92/0.92.3/январского среза путь присутствует, но журнал автора неизвестен.

Различия импорта, reverse и случайного/выводимого C дают точные условные модели, но не предоставляют неизвестные root/C/порядок автора. Дешёвое безусловное восстановление не получено; невозможность иных атак не доказана. Прежний архивный поиск не дал связанного с автором журнала/PKCC, новый всеобщий поиск в интернете здесь не запускался.

**Решение:** новый полный перебор не обоснован. Следующий достаточный материал — подтверждённый артефакт автора (root/public+C, подходящий журнал, исходный export с mapping) либо конкретный доказанный слабый источник внешних imported ключей. До этого Armory остаётся возможным, но не подтверждённым генератором.

## Приёмка и пределы

На каждом из двух профилей: **96 parser-кейсов, 18 маршрутов выбора root/C, 18 событий импорта, 24 фильтрованных списка, 72 строки key export, 18 ветвей одиночного диалога**. ACCEPTANCE.json — артефакт исходного исследования (`ACCEPTANCE.json`; вне снимка) указывает успешные runs и независимые VERIFICATION.json. Сравнены результаты Windows/Linux, хеши выделенных методов, source archives и прежние pins. FINAL_MANIFEST.json — артефакт исходного исследования (`FINAL_MANIFEST.json`; вне снимка) фиксирует новые артефакты.

Это выбранные исходники и выбранные операции. Остальные версии, полный native C++/PyQt4, binary-wallet migration, нестандартные сборки, реальные ОС/RNG-состояния, полный bulk/SecurePrint/fragmented импорт не объявляются проверенными. Исправления касались только адаптера стенда (isRegistered, штатная константа порядка, radioImport) и разбора пробелов в старом export; исходники Armory неизменны. Ошибочные попытки сохранены отдельно.

Повтор: `python -B run_native.py windows-amd64` или `linux64`, затем `python -B verify.py <путь/NATIVE.json>`. Нужны уже подготовленные соседние CPython2.7.9 runtimes и исходная зависимость ecdsa0.11 из Electrum-эксперимента; системная установка не выполняется. [PROTOCOL.md](<PROTOCOL.md>) описывает изоляцию и объём.
