# MSG-DB-01 — консольный аудит CoinDB

05.11.2026, Europe/Moscow. Запрос пользователя: продолжить mSIGNA, **без GUI**.

Объект: commit `ace0c828bed7441ef6ddda314674d882ecf4dbbe` от 13.01.2015. Предыдущий R2 исполнял CoinCore HDKeychain, но не CoinDB Keychain/Key. Здесь проверяется именно этот дополнительный слой.

1. `collect.py` копирует закреплённые источники предыдущего исследования и загружает недостающие файлы официального репозитория. Каждый исходник сверяется с Git blob из ранее сохранённого дерева commit; SHA256 записывается в SOURCES.json. Независимая Python-reference копируется без изменений.
2. `prepare.py` буквально извлекает классы Keychain/Key из Schema.h и их тела из Schema.cpp. Номера строк и хеши записываются в EXTRACTION.json. `odb::access` только объявлен; pragmas не обрабатываются. База данных и Qt не подключаются.
3. CoinCore HDKeychain/secp256k1/BigInt и остальные необходимые заголовки копируются без изменений. Из hash.h исключаются неиспользуемые Hash9/scrypt-зависимости; тестовой подстановки HMAC нет. В aes.cpp только контексты EVP переводятся со стека на EVP_CIPHER_CTX_new/free для OpenSSL3. Diffs сохранены. `BN_LONG=long` нужен для неиспользуемой старой перегрузки BigInt.
4. `run.py` собирает стенд g++ в имеющемся WSL Ubuntu и выполняет пять синтетических наборов. Используются настоящие Boost text archive и криптографические вызовы. Установка пакетов, запуск GUI, подключение к Bitcoin network, чтение настоящих кошельков и транзакции отсутствуют.
5. `verify.py` сверяет все записи с независимой аффинной моделью BIP32. Python отдельно вычисляет исторический EVP_BytesToKey/SHA1 с пятью раундами; AES-CBC проверяется отдельным openssl enc. Это независимая проверка формата/KDF, не независимая реализация самого AES.
6. `finalize.py` проверяет источники, извлечённые тела, build inputs, бинарник, stdin/stdout, verifier и reference. ACCEPTANCE и FINAL_MANIFEST фиксируют конкретный успешный run.

Входы: BIP32 vector1 seed, последовательность байтов 0…31, маркированная синтетическая строка, 32 нулевых и 32 FF-байта. Последние два — граничные контроли API, **не найденные слабые seed автора**. Их производные и все файлы `.priv` в runs синтетические.

Version-1 проверка вызывает неизменённый `load(...,1)` через Boost serialization access на явно сформированных полях. Это не файл, выпущенный настоящим старым установщиком. Version-2 round-trip использует стандартный `archive << object >> object`, но Boost 1.83, не библиотеку 2014 года.
