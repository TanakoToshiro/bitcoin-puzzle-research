# MSG-DB-01 — mSIGNA/CoinDB: дополнительные сценарии без GUI

05.11.2026, Europe/Moscow. **Впервые исполнены исторические CoinDB Keychain/Key и их сериализация: 335 результатов на пяти синтетических входах совпали с независимой моделью. Ошибочная private-child ветвь подтверждена и уточнена. Восстановления настоящего Puzzle и нового малого пространства для перебора не получено.**

Продолжение [первого исследования](<../parallel-wallets-20261102/03-msigna/RESULTS.md>) и [R2](<../parallel-wallets-20261102/03-msigna/round2/RESULTS.md>). Пользователь исключил GUI из задания; GUI не запускался. Предыдущие отчёты и их артефакты не менялись.

## Что именно проверено

Исходники mSIGNA `ace0c828bed7441ef6ddda314674d882ecf4dbbe`, commit от 13.01.2015 07:36:42 UTC. Шестнадцать файлов проверены по Git blob ранее закреплённого дерева; SOURCES.json — артефакт исходного исследования (`SOURCES.json`; вне снимка). Для CoinDB буквально выделены объявления Keychain/Key и соответствующие методы: EXTRACTION.json — артефакт исходного исследования (`EXTRACTION.json`; вне снимка). Это расширяет прежнюю native-проверку CoinCore; полного Vault/ODB-процесса не было.

Более ранний набор из305 записей сохранён как подготовительный этап; в итог он повторно не суммируется. Ни один тест не использует неизвестный приватный ключ автора.

## Private-child: где ошибка проявляется

Пусть настоящий parent — `(s,c)`, его правильный BIP32-child — `(s_i,c_i)`. В `Keychain::child(i,true,empty_lock)` сохраняется приватный скаляр **родителя s**, но публичная точка, chaincode и metadata берутся от child. Иными словами:

```text
сохранённый public:       (s_i·G, c_i)
после unlock, private:   (s,     c_i)
```

Это теперь подтверждено исполнением исходного CoinDB, не только моделью присваивания. Проверены normal и hardened indices. С непустым lock key исходный метод шифрует правильный `s_i`, и экспорт/round-trip совпадают с BIP32.

| Операция | Подтверждённое поведение |
|---|---|
| Прямой private BIP32 export ошибочного child | Скаляр parent и chaincode child. Его публичный эквивалент не совпадает с отдельным public export того же объекта. |
| Прямой `getSigningPrivateKey` от ошибочного child | Выводит новую последовательность из смешанной пары `(s,c_i)`. |
| `Key(child,7).try_privkey()` после одного ошибочного перехода | Идёт через `root()` и сохранённый derivation_path: получает правильный `root/i/7`. Ошибка хранения child сама по себе здесь не подменяет private leaf. |
| Boost export/import того же child | Parent-ссылка и derivation_path не сериализуются. После загрузки child становится отдельным root, и private leaf идёт уже из смешанной пары. |
| Второй подряд ошибочный private-child | Сохранённый scalar снова равен исходному s, но следующая public point вычислена уже от смешанного parent. Теперь публичный ключ `Key` может расходиться с private, вычисленным через первоначальный root и полный path. |
| Шифрование после создания ошибочного child | Сохраняет уже неверный scalar; ошибку не исправляет. |
| Непустой lock key на каждом private-child переходе | Даёт правильную последовательность, включая проверенный двухуровневый путь. |

Значение слова «ключ» в этих операциях различается: поле объекта, отдельный xprv export и приватный ключ `Key` нельзя подменять друг другом. Проверки не создавали и не подписывали транзакции; установлено расхождение/совпадение самих ключей.

Штатный `AccountBin::loadKeychains` вызывает **public** `child(index_)`; штатный `Key` получает private leaf от root с derivation_path. Поэтому private-child bug не доказан как обычный генератор mSIGNA. Понадобился бы дополнительный внешний вызов/API-сценарий автора.

Первичные источники: [child и Key](https://github.com/ciphrex/mSIGNA/blob/ace0c828bed7441ef6ddda314674d882ecf4dbbe/deps/CoinDB/src/Schema.cpp#L94), [сериализуемые поля](https://github.com/ciphrex/mSIGNA/blob/ace0c828bed7441ef6ddda314674d882ecf4dbbe/deps/CoinDB/src/Schema.h#L246).

## Импорт, состояние объекта и копирование

**xprv import хранит 33 байта `00 || s`.** Это штатный результат `HDKeychain.key()`, а не укороченный seed. `exportBIP32` и `getSigningPrivateKey` удаляют служебный ноль и работают правильно. `child(i,true)` не удаляет его и передаёт 33 байта в constructor, который считает их public point: вызов завершается `Invalid key`. Подтверждено и для plain, и для encrypted import. Public child работает. Импорт правильного extended child сохраняет относительную деривацию: импортированный `root/2` затем `/7` совпадает с прежним `root/2/7`.

Дополнительные нестандартные состояния:

- **Copy constructor Keychain не копирует hash_.** Получается пустая identity при сохранении ключевых полей; xprv export прежний. `operator=` пересчитывает identity, но сохраняет имя destination. Эти операции дают разные metadata, не разные случайные seed. Достижимость именно copy constructor в стандартном экспорте не установлена: просмотренный `Vault::exportKeychain` работает через shared_ptr, без такого копирования.
- **Прямой importPrivateKey не проверяет соответствие исходной пары и не сбрасывает уже открытый cache.** В контроле сначала виден старый private, после lock/unlock — scalar второго объекта при старых public/C. Это API misuse на двух синтетических keychains. Штатный Vault вызывает его после поиска по сохранённому hash и при добавлении private к public-only объекту; нельзя переносить тест прямого несовместимого вызова на любой штатный импорт.
- **Повторный importBIP32 в уже дочерний объект сохраняет parent/path.** Public данные заменяются, а `Key` может продолжить получать private по старому root/path. Просмотренный Vault создаёт новый Keychain перед importBIP32; этот сценарий требует повторного использования объекта внешним кодом.
- **Lock/clear** проверены: закрытый private-child отвергается; `Key::privkey` при закрытом root возвращает пустой вектор, `try_privkey` бросает исключение. `clearPrivateKey` удаляет private-состояние. Это не успешное создание нулевого ключа.

Источники: [Keychain declaration/copy/load](https://github.com/ciphrex/mSIGNA/blob/ace0c828bed7441ef6ddda314674d882ecf4dbbe/deps/CoinDB/src/Schema.h#L156), [import/export methods](https://github.com/ciphrex/mSIGNA/blob/ace0c828bed7441ef6ddda314674d882ecf4dbbe/deps/CoinDB/src/Schema.cpp#L213), [Vault import](https://github.com/ciphrex/mSIGNA/blob/ace0c828bed7441ef6ddda314674d882ecf4dbbe/deps/CoinDB/src/Vault.cpp#L766).

## Архивы и шифрование

Настоящий Boost v2 round-trip в стенде сохранил root/public/keychain data. Для дочернего объекта подтвердилось отсутствие parent/path после загрузки. Это проверка схемы полей на Boost1.83; побайтовая совместимость со всеми архивами Boost2014 не утверждается.

В неизменённом `load(ar,1)` прежние vector-поля chaincode salt и private salt читаются и отбрасываются; `privkey_salt_` устанавливается в0. На **синтетической последовательности полей v1** plain scalar сохраняется, а 48-байтный ciphertext трактуется как plain и приводит к `Invalid key` при export. Это показывает контракт loader, но не доказывает, что конкретный старый релиз выпускал именно такой encrypted v1-файл. Полного старого writer/исторического файла в этом этапе нет. Версия схемы Boost и legacy123-byte CoinQ — разные форматы.

Реальный AES-код использует AES256-CBC и `EVP_BytesToKey(SHA1,5)`, salt — восемь байтов в представлении uint64 текущей платформы. Для фиксированного little-endian salt получены пять совпадений с отдельно вычисленным Python KDF + openssl enc. Проверены правильный и один неправильный lock key, encrypt/decrypt и encrypted-child round-trip. Отказ выбранного неправильного ключа не является доказательством аутентичности CBC или невозможности случайного корректного padding.

В random.h — артефакт исходного исследования (`sources/deps/CoinCore/src/random.h`; вне снимка) источником служит OpenSSL RAND_bytes; salt также получается оттуда. Здесь не воспроизводились entropy-состояния старых ОС или OpenSSL. Нулевой/FF entropy был явно задан **стендом**. Никакой связи passphrase с генерацией root из этих проверок не следует: lock key используется для хранения уже имеющегося private.

## Применимость к Puzzle и раннему коду

Из прежнего R2 сохраняются результаты: двенадцать просмотренных редакций HDKeychain с декабря2013 используют аддитивный BIP32; legacy CoinQ имеет собственный123-byte экспорт и другой способ создания keychain. Они не перекомпилированы здесь и не становятся CoinDB вследствие сходного имени. Новая native-проверка относится к указанному январскому срезу.

Сценарий «всегда экспортировать сохранённый scalar ошибочного private-child без дальнейшей CKD» по-прежнему даёт один и тот же raw s. Он уже отвергнут известными решениями №2 и №4 в первом исследовании: несовместимы `s mod2=1` и `s mod8=0`. Рекурсивное повторение этой ветви при пустом lock key само по себе не устраняет постоянство сохраняемого scalar.

Если после ошибочного export/import выполняется правильная CKD из `(s,c_i)`, значения уже различаются. Эта модель **не исключена** тестом постоянного raw, но требует неизвестных s и c_i. Из опубликованных маскированных решений HMAC-коэффициенты не становятся известными. Никакого ограниченного домена seed или остатка ≤2^32 не найдено; полный перебор не запускался.

Настоящий root/bin xpub, account/keychain export или иной связанный с автором артефакт в задании отсутствует. Прежние исследования таких кандидатов не предъявили; новый всеобщий архивный поиск не проводился. Поэтому применение восстановления к настоящим данным автора остаётся **невыполненным из-за отсутствия требуемого входа**, а не отрицательным результатом. Для дефектного объекта особенно важно проверить согласованность public/private и способ его использования: public export может описывать не ту последовательность, которую создавал private API.

**Итог:** закрыта конкретная часть оставшихся nongui-сценариев — исполнение CoinDB, хранение private-child, повторные вызовы, copy/assignment и выбранная сериализация. mSIGNA как источник Puzzle не исключён. Все произвольные API-композиции, полный Vault/ODB, старые бинарные сборки, весь RNG/entropy и настоящие архивы иных версий не объявляются проверенными. Следующий обоснованный вход — артефакт автора либо конкретный подтверждённый способ получения внешнего seed.
