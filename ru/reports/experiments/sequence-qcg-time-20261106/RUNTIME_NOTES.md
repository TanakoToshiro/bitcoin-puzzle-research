# Обвязка и границы профиля

До успешной валидации были сохранены две технические ошибки, не результаты поиска: validation_a не дошёл до Python worker из-за передачи пути с пробелами через bash; validation_a2 построил малую модель, но остановился до check при обращении к удалённому приватному атрибуту z3core._lib. В validation_a3 используются прямой wsl --exec, RLIMIT_AS в отдельной Python-обёртке и проверка реально загруженной библиотеки через /proc/self/maps или GetModuleFileNameW. Исходные ошибочные файлы/логи не переписаны. Формулы при исправлениях не менялись.

Linux имеет 180 с внешнего времени на профиль вместо 150 с Windows из-за запуска WSL и загрузки файлов через /mnt/c; внутренний check у всех трёх библиотек равен 120 с. Для Linux ограничивается виртуальное адресное пространство (RLIMIT_AS=2 GiB), для Windows — working/private (2 GiB). Это диагностические ресурсные границы разных ОС, не парное сравнение пиковой памяти. Контроль и профиль Linux собраны одинаковыми флагами; частоты этапов и времена этого профиля не объявляются точной процентной раскладкой Windows.

Диагностическая сборка принудительно использует Z3_FF_HAS_UINT128=0; это исключает платформенное включение F4 в GCC. Отсутствие __uint128 у MSVC не является само по себе полным доказательством флагов поставленной Windows DLL. Установленная DLL не меняется; пригодность параметров и ускорение проверяются отдельно на ней.

Валидируются десять старых точных малых входов на каждой Linux-библиотеке. Дополнительно положительный полностью известный пример p=17 и старое противоречие dependency вызывают Tactic(smt) непосредственно с ff.root_split=false и solve_eqs=false, чтобы проверить нативный путь и сбор счётчиков. Эти специальные настройки используются только для диагностической валидации; полноразмерный профиль сохраняет исходную стратегию SEQ-26.
