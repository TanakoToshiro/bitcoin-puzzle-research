# SEQ-27 — время совместного QCG-решателя

Дата: 06.11.2026. Объём эксперимента завершён; математическое восстановление остаётся открытым.

## Результат

При неизменной формуле `ff.fused_reduction=true` вместе с `ff.preprocess=false` повысил скорость получения нативных конфликтов в 3.67–6.00 раза на шести сохранённых входах; совокупное отношение скоростей 4.56×. За 120 секунд на вход получено суммарно 146 конфликтов вместо 32. Это измеренное ускорение обработки проверяемых ветвей, а не доказанное ускорение полного восстановления.

Все 12 основных запусков остались `unknown / timeout`. Восстановлений четырёх положительных цепочек 0/4; окончательных ответов по шести входам 0/6. Таймаут не является отрицательным ответом. Реальные ключи не исследовались; новых состояний/ключей/битов нет.

## На что уходит время

На неизменной установленной Windows DLL исходный full00: check 120.070 с, CPU 117.438 с, шесть нативных проверок. Таким образом, процесс занят вычислениями. Старые `ff solve seconds` около 2.7 с описывают начальный этап, а не все последующие вызовы нативной теории.

В source `theory_ff::check_native` каждый раз создаёт новый `ff::solver`; старая сводка не собирает его времена. Добавлены только часы и счётчики в четыре файла точного коммита Z3. Исправленная диагностическая запись A4:

| Стадия | Секунды |
|---|---:|
| Весь `solver.check()` | 120.075 |
| Все нативные проверки | 117.242 |
| `algebra.solve` внутри них | 112.909 |
| Кодирование и подготовка нативных входов | 3.696 |
| В том числе `prepare` | 3.358 |
| Сбор текущих равенств | 0.235 |
| Объяснение конфликтов | 0.059 |

Строки вложены друг в друга; их нельзя складывать. Около 94.0% измеренного check приходится на решение алгебраических систем. Получено 12 нативных вызовов, 11 конфликтов; 11 промахов кэша базиса, попаданий нет. Это локализует основной расход после подготовки формулы. Отдельные доли исключения переменных, редукций и базиса не измерены.

Диагностика собрана в Ubuntu/WSL, потому что доступная Windows MSVC не содержит стандартных C++ заголовков. Чистая и инструментированная локальные сборки имеют одинаковые Release-флаги, включая `Z3_FF_HAS_UINT128=0`. Обе прошли по 10 точных малых эталонов и по 2 прямых SMT-контроля; full00 в A3 дал 11 вызовов на каждой. Windows за то же время дал 6: численные доли Linux нельзя выдавать за точный Windows-профиль. Все сравнения ускорения ниже выполнены на исходной установленной Windows DLL.

## Что изменено

Основной режим: `ff.preprocess=false, ff.fused_reduction=true`. Все прочие математические и поисковые параметры прежние; seed 0. В `ff_polynomial.cpp:820–839` редукция обновляет F := F + scalar·monomial·G напрямую, вместо построения промежуточного произведения и последующего сложения. Сохраняются используемые предпосылки и точная арифметика поля. Число внутренних шагов может отличаться: результат сравнения относится к реализации с прежним численным бюджетом, а не к идентичной последовательности всех событий.

Ни одного ограничения не удалено: 135 состояний, 134 квадратных связи z=s², 134 перехода с общими a,b,c, a≠0, точные границы целых представителей и прежний gauge. Полноразмерная формула: 17497 переменных, 17659 утверждений. Исходные 83 маски и пропуски сохранены, всего 3767 наблюдаемых битов; скрытые биты и свидетели не передаются поисковому процессу. Хеш каждого тела SMT совпал со старым SEQ-24. Изменены только параметры алгоритма.

## Выбор варианта и парная проверка

План B зафиксирован до пилота. На full00 по 60 с: baseline — 2 конфликта; fused — 13; buckets — 13; bounded — 2. Bounded вернул timeout через 83.98 с, показав запаздывание мягкого таймера; внешний предел 90 с сохранён. Fused выбран по зарегистрированной скорости конфликтов; разница с buckets на пилоте практически ничтожна и не доказывает превосходство одного над другим. Все четыре режима прошли 40/40 малых проверок по архивному полному перебору 360536 кортежей. Контроль dependency остался UNSAT.

## Проверка выбранной скалярной редукции

После завершения измерений дополнительно проверены 8 задач над p=17 и настоящим n, в обоих режимах. Уравнения x·y=1, y=x², y²=k: при k=1 свидетель x=y=1; при k=3 из x³=1 и x⁴=3 следует x=3, что противоречит 27≡1 (ни один модуль не делит 26). Все ответы совпали с этими доказанными эталонами. Для контроля отключены F4/пакетный/малополевой пути, и статистика каждого fused-запуска подтвердила выполнение fused reductions. Эти служебные параметры не применялись в основной серии. SCALAR_VALIDATION.json — артефакт исходного исследования (`SCALAR_VALIDATION.json`; вне снимка), AUDIT_EXTRA.json — артефакт исходного исследования (`AUDIT_EXTRA.json`; вне снимка).

RESULTS.json — артефакт исходного исследования (`RESULTS.json`; вне снимка), COMPARISON.json — артефакт исходного исследования (`COMPARISON.json`; вне снимка), [PROTOCOL_B.md](<PROTOCOL_B.md>), PLAN_C.json — артефакт исходного исследования (`PLAN_C.json`; вне снимка) содержат полные показатели и условия. CLOSURE.json — артефакт исходного исследования (`CLOSURE.json`; вне снимка) связывает новые попытки со старыми открытыми входами.

Повторять в новую папку вне запечатанного эксперимента через `replay_case.py full00 --mode fused --output <новая-абсолютная-папка> --timeout-ms 120000 --memory-mib 2048`, используя исследовательский `.venv/Scripts/python.exe -B`. Скрипт применяет те же API-параметры и внешние лимиты. Это запуск с начала, не продолжение checkpoint.

Технические поправки не скрыты: две ранние попытки запуска завершились до check из-за пути WSL и определения загруженной библиотеки. В A3 повторяющиеся значения диагностической статистики ошибочно читались как первое значение; эти подробные показатели не используются для выбора. Worker v3 сохраняет все записи и суммирует их, A4 проверяет равенство числа экземпляров и нативных проверок. [STATISTICS_CORRECTION.md](<STATISTICS_CORRECTION.md>) сохраняет объяснение. Дополнительный более глубокий профиль не был собран: WSL перезапустился и очистил временное дерево сборки; отказ произошёл до изменения исходников. Сохранённых архивов и готовых контрольной/инструментированной библиотек это не затронуло.

Для дальнейшего точного поиска имеет смысл сохранить найденную оптимизацию. Основной открытый вопрос теперь — получение более сильных ограничений на ветви без угадывания полного набора битов; этот эксперимент не разработал такого метода.
