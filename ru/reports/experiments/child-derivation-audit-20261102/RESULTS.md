# HD-01 — исторические кошельки и связи дочерних ключей

02.11.2026. **Первый цикл завершён. Самые подходящие по удобству исходного сценария — Armory classic и Electrum1.9.8. Найден и проверен условный способ восстановить256-битный Armory-корень по частичным дочерним ключам без слабого seed. Для настоящего Puzzle он пока неприменим: требуются правильные watch-only root public key и chaincode, которых у нас нет. Только из известных решений и кода нового практического поиска до2^32 не получено.**

## Отбор программ

Использован исторический каталог bitcoin.org от14.01.2015 и код соответствующего времени. Это подтверждает доступность/известность, но не позволяет ранжировать доли рынка или вероятность использования автором. Подробности и первичные ссылки: [WALLETS.md](<WALLETS.md>), SOURCE_FACTS.json — артефакт исходного исследования (`SOURCE_FACTS.json`; вне снимка).

- **Armory:** GUI увеличения address pool на заданное число и Export Key Lists с включением неиспользованных адресов, приватных ключей, ChainIndex. Сотни ключей действительно предусмотрены интерфейсом. Это самый прямой просмотренный путь для последующего простого скрипта.
- **Electrum1.9.8:** изменение gap limit/генерация пула, экспорт address/private_key в CSV и dumpprivkeys. По умолчанию старая Electrum-деривация, также есть опциональная BIP32. Для всех этих путей не требуется слабость seed.
- **mSIGNA:** desktop BIP32, экспорт keychain/extended private key. Массовая деривация после такого экспорта возможна скриптом, но прямой GUI-export256 WIF не подтверждён.
- **bitcoinj0.12 / Bitcoin Wallet:** стандартная HD-цепочка и WalletTool с lookahead/dump-privkeys. Для мобильного кошелька путь к массовой выгрузке менее удобен. Под капотом это ещё одна BIP32-модель, не новое математическое семейство.
- **Core0.9.3:** массовый keypool возможен, но общего детерминированного родителя в исследованном штатном пути нет. Остальные бренды из каталога не объявляются исключёнными; их полный аудит экспорта пока не выполнен.

Просмотрены штатные методы и UI-вызовы, старые GUI целиком не запускались. Порядок экспорта может включать receiving/change, accounts и imported keys; следовательно, номер puzzle не автоматически совпадает с child index. Неподтверждённые перестановки не перебирались.

## Новый положительный результат: Armory + частичные ключи

Штатная классическая Armory-цепочка мультипликативная: следующий скаляр равен предыдущему, умноженному на значение из chaincode XOR doubleSHA256 исходной публичной точки. Если известны **корневая публичная точка и chaincode**, все множители можно вычислить через публичный путь, без приватного корня. Тогда несколько младших остатков производных дают Hidden Number Problem; её можно решить решёткой вместо перебора корня.

Реализованы LLL, точный Babai и проверка кандидата по root public key. На12 искусственных кошельках полного secp256k1-размера корень восстановлен по четырём masked ключам, соответствующим известным индексам120/125/130/135. Это119/124/129/134 наблюдаемых младших бита, а не полные исходные child keys. Остальные79 известных индексов каждого случая использованы после восстановления. Все12 успехов,36 отрицательных контролей и независимые affine-проверки прошли.

Отдельный процесс `recover_watchonly.py` получил только watch-only параметры и четыре masked private key с номерами, самостоятельно посчитал коэффициенты и тоже восстановил12/12. Приватный корень, seed и полные raw children на вход ему не передаются. Само восстановление заняло примерно4–6мс, вместе с публичной цепочкой — около12–20мс на этой машине, без времени запуска Python. Точные измерения — [NUMERIC_REPORT.md](<NUMERIC_REPORT.md>). Два официальных Armory child-вектора и20 проверок прежним независимым reference подтверждают, что используется нужная историческая формула.

**Это условный synthetic результат, а не найденный ключ Puzzle.** Watch-only данные не равны адресу и не появляются в блокчейне автоматически. Один chaincode без нужной исходной публичной точки здесь недостаточен. Мы не обнаружили эти параметры автора и не восстановили их из имеющихся решений. HNP/LLL — известный класс методов; новизна в мировой литературе не заявляется. Новый вклад относительно нашей E3/E6H — работающий полный по размеру восстановитель root из частичных children при публичных коэффициентах, без предположения короткого seed.

## Electrum и BIP32: другой результат

Здесь дети имеют аддитивную форму `child=(parent+offset) mod n`. Offset вычисляется из MPK либо xpub/chaincode через SHA/HMAC. Без этих параметров известные младшие биты children не превращаются в систему с известными коэффициентами. Простое вычитание children оставляет неизвестные хешовые добавки.

Для ситуации с уже известным xpub реализовано точное пересечение всех модульных условий с учётом переносов modulo n.800 исчерпывающих малых контролей прошли. В24 полноразмерных синтетических случаях с83 известными индексами оставалось примерно2^114.78–2^117.69 **арифметических кандидатов до проверки связи parent_private*G=parent_public**. Это не число действительных ключей одного xpub, не энтропия и не нижняя граница любой атаки. Проверенный способ до2^32 не дошёл.

При известном xpub меньший masked child при этом можно предсказать по более длинному известному остатку с учётом трёх вариантов переносов.48 тестов прошли,96 неверных параметров отвергнуты. Это расширение прежнего E7 с Electrum на non-hardened BIP32-пути, не впервые открытый эффект. Hardened-граница отдельно проверена: публичного xpub недостаточно для деривации через неё. Восстановление account private key также не означает обращения hardened-перехода к исходному master/seed.

Формулы, доказательство точности арифметического счёта, решёточное построение и ограничения: [MATH.md](<MATH.md>). Сумма3767 наблюдаемых битов не означает, что их можно независимо вычесть из256 или512 неизвестных битов. Единственность решения и низкая стоимость его нахождения — разные свойства.

## Что не повторялось и что не установлено

Не повторялись501 MPK-кандидат E7,48 схем №256, прежние Armory XOR-MITM/feedback запросы, RNG-переборы и HASH160 ML. Прежние результаты не изменены. Взяты83 проверенных решения сохранённого snapshot до№135; новые внешние решения не добавлялись. Все12 новых корней, цели71/100 и holdout этого исследования — специально созданные synthetic данные. Настоящего нового приватного ключа или бита нет.

Известного root public/chaincode для реальной Armory-цепочки нет; при неизвестных параметрах коэффициенты HNP не построены. Публичные точки **изменённых** puzzle-ключей нельзя подставить вместо исходных raw-точек. Ранее рассмотренный E6H неизвестного chaincode остаётся отдельной сложной задачей; новый положительный результат её не решает.

## Следующие эксперименты

1. **Конкретные Armory watch-only артефакты автора:** корневая публичная точка вместе с chaincode, либо более ранняя публичная точка той же цепочки с подтверждённым индексом и chaincode. Искать только в источниках, связанных с Puzzle; простое перечисление произвольных root/chaincode снова даст огромное пространство. Результат должен быть набором проверяемых кандидатов, который сразу можно прогнать через готовый восстановитель.
2. **Совместное восстановление неизвестных параметров Armory.** Новая математическая постановка — использовать masked private observations вместе с доступными исходными/условными публичными точками для определения коэффициентов. До больших вычислений нужен конкретный алгоритм и тест, показывающий сокращение стоимости относительно предыдущего XOR-MITM; запуск того же solver дольше не является новым методом. Сейчас такого алгоритма нет.
3. **Дополнение карты удобных кошельков** — конкретные старые Hive/breadwallet/Mycelium и более ранние версии, только если найдётся иной алгоритм либо существенно иной экспорт. Повтор стандартного BIP32 под новым названием не добавляет независимой атаки. Раннюю мультипликативную редакцию BIP32 исследовать лишь при подтверждённом приложении/версии, а не по одному существованию старого проекта стандарта.

GPU/MSVC/SX не затронуты. Код, источники с URL/UTC/SHA-256, входы решёток, transforms, результаты, ошибки, версии и команды сохранены. Приёмка — ACCEPTANCE.json — артефакт исходного исследования (`ACCEPTANCE.json`; вне снимка); общий файл исследований дополнен новой записью.
