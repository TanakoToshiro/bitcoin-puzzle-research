# Исторический отбор по удобству массовой генерации

Крайняя дата —15.01.2015. Основание известности: [каталог bitcoin.org на14.01.2015](https://github.com/bitcoin-dot-org/bitcoin.org/blob/bbdc9f893743b051216650bd2821f4b810e061f4/_templates/choose-your-wallet.html), где перечислены все основные названные ниже пользовательские кошельки. Долей рынка/числа активных пользователей не установлено; это не рейтинг популярности и не атрибуция автора Puzzle. Приоритет ниже — соответствие сценарию «получить сотни private keys → изменить внешним скриптом».

| Кандидат | Исторический путь | Семейство | Приоритет для этой задачи |
|---|---|---|---|
| Armory classic,08.01.2015 | GUI Extend Address Pool принимает число адресов; Export Key Lists умеет Include Unused (Address Pool), приватные ключи и ChainIndex | Собственная последовательная мультипликативная цепочка | Первый: наиболее прямой подтверждённый GUI-сценарий |
| Electrum1.9.8,16.03.2014 | Увеличение gap limit через console/API, синхронизация пула; GUI Wallet→Private Keys→Export CSV; есть dumpprivkeys | По умолчанию old Electrum, также опциональный BIP32 | Первый: короткий путь и удобный CSV |
| mSIGNA,13.01.2015 | GUI экспорт private keychain/BIP32 extended key; дальнейшая массовая деривация в небольшом скрипте | BIP32, приложение ориентировано на multisig | Второй: прямой массовый CSV child private keys в просмотренном UI не подтверждён |
| bitcoinj0.12 / Bitcoin Wallet того периода | Библиотека HD, WalletTool с lookahead-size и dump-privkeys; мобильный интерфейс сам по себе менее удобен для выгрузки сотен ключей | BIP32 m/0'/0/i, m/0'/1/i | Второй: хорошая техническая модель, более сложный пользовательский экспорт |
| Bitcoin Core0.9.3 | keypool + dumpwallet позволяют много ключей, но в проверенном срезе они генерируются независимо | Нет штатного общего HD-родителя | Вне математической задачи о дочерних связях |
| MultiBit Classic из каталога | Известный desktop-кандидат, экспорт ключей возможен, но современный MultiBit HD нельзя автоматически переносить назад | Точную архивную цепочку Classic здесь заново не аудировали | Не включён в положительный HD-shortlist без отдельного подтверждения |

Electrum, Armory и mSIGNA в каталоге указаны для Windows/Linux/macOS. Bitcoin Wallet — Android/BlackBerry. BX/SX удобны для script-driven generation, но это уже текущие исследования и CLI-инструменты, а не новая пользовательская shortlist. Trezor, Mycelium, Hive, breadwallet также присутствуют в каталоге; полный исторический аудит их private-key экспорта в этом первом проходе не выполнен. Их нельзя объявлять исключёнными. Расширять список стоит ради нового доступного способа деривации/экспорта, а не количества брендов с тем же BIP32.

## Что именно подтверждено в коде

**Armory.** В qtdialogs.py класс Extend Address Pool вызывает fillAddressPool с заданным naddr; при naddr≥1000 выдаётся дополнительное подтверждение, то есть сотни предусмотрены интерфейсом. DlgShowKeyList берёт `getLinearAddrList(withAddrPool=True)`, предлагает Include Unused, формат приватного ключа и ChainIndex. Метод возвращает порядок записей wallet file, не произвольную сортировку по адресу. Однако импортированные ключи могут присутствовать; при них порядковый номер строки не равен chainIndex. Root отдельно доступен как Include Paper Backup Root; его наличие нельзя молча предположить для обычного child-экспорта. Сохранённый срез: etotheipi/BitcoinArmory `61a596fa94f9cacf9fb00c4e02d0eb65d8b17513`. Формула деривации уже независимо проверена E3; повтор той же реконструкции не делался.

**Electrum.** В [GUI export](https://github.com/spesmilo/electrum/blob/f92b483942d3f8ee51506e0436d9b524db33a336/gui/qt/main_window.py#L1939) CSV содержит address/private_key, цикл проходит `wallet.addresses(True)`. `change_gap_limit` увеличивает требуемый пул, синхронизатор создаёт новые адреса. Встречаются receiving/change, несколько accounts и imported keys. Следовательно, простой экспорт не доказывает stride1 на одной ветке. Получение Hundreds через изменение gap limit требует выполнения генерации/синхронизации; изменение одного числа само по себе не объявляется уже состоявшимся экспортом.

**mSIGNA.** `KeychainModel::exportKeychain(...,exportPrivate)` и `getExtendedKeyBytes(...,getPrivate)` передают запросы в Vault; `HDKeychain::getChild` использует HMAC-SHA512, big-endian index и сложение IL с parent modulo n. Публичный и приватный режимы разделены, hardened от публичного ключа запрещён. Возможность экспортировать xprv позволяет использовать стандартную деривацию, но не доказывает наличие GUI-кнопки «экспортировать256 WIF».

**bitcoinj.** В версии0.12 есть DeterministicKeyChain и инструменты `--lookahead-size`, `--dump-privkeys`; модель normal/hardened определена в HDKeyDerivation. Путь от приложения до удобного массового экспорта хуже, чем у первых двух кандидатов. Историческая миграция старых ключей в seed уже исследовалась E9, здесь её не используем как слабость.

Все выводы об интерфейсе основаны на сохранённых исходниках, а не на запуске старых GUI целиком. Источники/строки/хэши — SOURCE_FACTS.json и SOURCES.json. Код генерации и порядок экспортных данных важнее внешнего сходства адресов. Само наличие wallet в каталоге не доказывает, что им пользовался автор Puzzle.
