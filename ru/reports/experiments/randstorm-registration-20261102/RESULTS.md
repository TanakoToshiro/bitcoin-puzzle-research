# RND-02 — регистрация My Wallet и Chrome 31

**02.11.2026. Проверка завершена. Для My Wallet от 29.12.2013 в обычном Chrome 31 на Windows обоснования для массового Randstorm-перебора не найдено. Приоритет этой конкретной комбинации снижен.** Это не исключение всех версий Randstorm и не установление программы автора puzzle.

## Браузер: системная энтропия доступна

Выбран Chrome 31.0.1650.63, официально выпущенный 04.12.2013 для Windows/Mac/Linux. Его [.DEPS.git](https://github.com/chromium/chromium/blob/31.0.1650.63/.DEPS.git) фиксирует Blink `bc61f1eac8b9db35dc87415c17cba319f6d55152`.

[WindowCrypto.idl](https://chromium.googlesource.com/chromium/blink/+/bc61f1eac8b9db35dc87415c17cba319f6d55152/Source/modules/crypto/WindowCrypto.idl) выставляет window.crypto без runtime-условия. [Crypto.idl](https://chromium.googlesource.com/chromium/blink/+/bc61f1eac8b9db35dc87415c17cba319f6d55152/Source/modules/crypto/Crypto.idl) явно говорит: getRandomValues доступен даже при отключённом экспериментальном флаге Crypto. Только subtle зависит от этого флага. Отсутствие полной Web Crypto API в старом браузере нельзя приравнивать к отсутствию getRandomValues.

Прослежена цепочка по закреплённым исходникам:

```text
window.crypto.getRandomValues(Int32Array32)
→ Blink Crypto::getRandomValues
→ WTF cryptographicallyRandomValues
→ WebKit sourceFunction → Platform::cryptographicallyRandomValues
→ Chromium WebKitPlatformSupportImpl → base::RandBytes
→ RandUint64 → Windows rand_s
```

WTF использует собственный ARC4 с периодическим подмешиванием 128 байт от системного источника и отбрасыванием первых 256 байт потока. Это **другое состояние**, не JSBN RC4 кошелька. Наличие ARC4 в обоих слоях не сводит системную энтропию к состоянию Math.random.

Источники: [WebKit.cpp](https://chromium.googlesource.com/chromium/blink/+/bc61f1eac8b9db35dc87415c17cba319f6d55152/Source/web/WebKit.cpp), [WTF RNG](https://chromium.googlesource.com/chromium/blink/+/bc61f1eac8b9db35dc87415c17cba319f6d55152/Source/wtf/CryptographicallyRandomNumber.cpp), [Chromium platform](https://github.com/chromium/chromium/blob/31.0.1650.63/webkit/child/webkitplatformsupport_impl.cc#L734), [Windows rand_s](https://github.com/chromium/chromium/blob/31.0.1650.63/base/rand_util_win.cc).

Полный старый браузер не запускался. Его цепочка установлена исходниками; JS-контроли получают явно заданные синтетические WebCrypto-слова. Компрометация ОС, подмена API расширением и нестандартные сборки не проверялись.

## Регистрация: пароль добавляется до первого ключа

Исполнен **полный неизменённый wallet-signup.js**, включая document.ready, обработчик кнопки, асинхронный UUID callback и проверки пароля. BitcoinJS bundle и точные функции _seed/generateNewKey взяты из принятого RND-01. DOM, ответы сервера и хранение заменены перечисленными в коде заглушками. Полный wallet.js и интерфейс сайта не запускались; шифрование после первого ключа является явной заглушкой.

Порядок успешной регистрации в этих контролях:

```text
загрузка BitcoinJS: WebCrypto → pool
document.ready → мышь/клавиша → Continue
UUID request → body click → UUID callback
проверка пароля → generateNewKey(password)
_seed: время, пароль, server seed при наличии
первый nextBytes → KSA → приватный ключ → сохранение
```

Четыре штатных успешных сценария имеют по одному WebCrypto-запросу и ноль Math.random-вызовов. Первая KSA наступает после _seed. Изменение раннего пароля, системных слов или server seed меняет ключ. Это проверка влияния входов, не оценка их энтропии.

Ошибки UUID, короткий пароль и несовпадающие пароли не достигают генератора. Если адрес уже есть, новый ключ не создаётся. Искусственно вставленный ранний nextBytes обнаруживается как ранняя KSA — положительный контроль детектора. Но **даже в нём системная энтропия уже присутствует в pool**. Такой обход сам по себе не даёт перебор состояния V8.

Контроль без WebCrypto даёт 128 вызовов Math.random, однако это искусственное отключение API, а не описание обычного Chrome 31.

[Числовой отчёт](<NUMERIC_REPORT.md>), трассы — артефакт исходного исследования (`TRACES.json`; вне снимка), приёмка расчётов — артефакт исходного исследования (`AUDIT.json`; вне снимка): 10 сценариев, 6 синтетических ключей. Независимо проверены RC4 по захваченной KSA, JSBN modulo, полные публичные точки и адреса через affine-EC. Настоящие puzzle-ключи не перебирались, скорость поиска не измерялась.

## Предел отрицательного вывода

Прямые потребители SecureRandom найдены в signer.js и sharedcoin.js: SMS-миниключи, подписи и операции SharedCoin. Само определение функции поток не расходует. В исследованном signup-коде эти функции не вызываются до _seed. Mnemonic modal и загрузка paper-wallet следуют после успешного сохранения.

Однако полный состав развёрнутой страницы не восстановлен. Старый WalletServlet ссылается на `bitcoin-wallet-new.jsp`, отсутствующий в закреплённом дереве. Два точных web-запроса также не дали этого артефакта. Поэтому результат относится к проверенному клиентскому пути, а не к любым скриптам, когда-либо размещённым на сайте. Качество серверного extra_seed тоже не установлено.

## Решение и продолжение

**Не писать GPU-сканер и не арендовать карту для этой комбинации.** Уже при загрузке поступает системная энтропия; нормальная регистрация дополнительно вносит пароль до KSA. Дешёвый путь обхода не найден.

Возврат к Randstorm оправдан при конкретном новом основании:

1. Точный браузер и более ранний wallet-срез, где getRandomValues действительно не используется. Срез 25.12.2012 из RND-01 остаётся кандидатом, но его браузер, события и дополнительные входы пока не зафиксированы. В этот этап он автоматически не включался.
2. Подтверждённая ошибка инициализации системного источника. Искусственно отключённый API такой ошибкой не является.
3. Отдельная историческая цепочка **SharedCoin**: 18 байт из SecureRandom сохраняются с префиксом `sharedcoin-seed:`, а `generateAddressFromCustomSeed(seed,n)` получает ключ через SHA256(seed+n), где n преобразуется в десятичную строку. Это детерминированная схема без BIP32, отличная от обычного generateNewKey. Она сохранена как будущая гипотеза. Seed от этого не стал коротким; связь с puzzle, маскирование, индексы и восстановимость не проверены. Массовый поиск по ней не обоснован.

## Артефакты и сохранность

Прежние 78 файлов RND-01 проверены и неизменны. SX не затронут. Все успешные источники имеют хэши; Git blob проверки и декодированные Gitiles-файлы перечислены в SOURCE_AUDIT.json. Команды — README.md, промежуточные выводы — JOURNAL.md, итоговый манифест — COMPLETE.json.

При подготовке обнаружена перезапись трёх ранних HTTP404-ответов унаследованным downloader. Их исходные хэши и метаданные сохранены в ERROR_BODY_LOSS.json и SOURCES_BEFORE_REPAIR.json; потеря тел явно обозначена. Успешные исходники не пострадали, downloader исправлен.
