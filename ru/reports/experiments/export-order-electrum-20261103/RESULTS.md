# EXP-01 — исторический порядок экспорта Electrum

**Точный порядок Electrum1.7.4 CSV воспроизведён и совпал с настоящим CPython2.7.9 на Windows x86/x64 и Linux x86_64.** Проверено21 сочетание платформы/hash-режима,252 CSV-файла,76776 строковых/контрольных хешей,546 снимков таблиц. Все совпадения точные; CSV побайтно, включая Windows CRCRLF из исторического open("w+").

Исследование синтетическое. Ни raw/master автора, ни новый ключ Puzzle не восстановлены. Полный PyQt GUI не запускался: исходные методы выполнялись в реальном Python2 с адаптерами UI/storage/данных; WIF-поставщик1.9.8 подставной. Историческая приватная деривация1.7.4 сверена с независимым coincurve расчётом.

## Что установлено

- Electrum1.7.4 собирает новый address→WIF dict и экспортирует items(). Перестановка зависит от raw-адресов, исходного master, hash-secret, истории вставок и размера таблицы. Сортировка по hash не воспроизводит probing/resizing. Нельзя вычислить одну универсальную перестановку для всех seed.
- Electrum1.9.8 в проверенном чистом OldWallet идёт по addresses(True): receiving-блок, затем change-блок. Импорты дают префикс, чей внутренний порядок зависит от dict; произвольные old accounts этим не обосновываются.
- В штатном примере1.7.4 все3 change-ключа оказались внутри первых256 строк. Поэтому export259→take256 не равен receiving-only256. В1.9.8 чистого R256/C3 первые256 — receiving.
- Windows x86/x64 имеют C long32; size_t32/64 различаются. В данном default-wallet они дали одинаковый порядок, но контроль160 отрицательных коллизий различие выявил. Linux LP64 имеет long64/size64.
- CPython2.7.9 по умолчанию отключает hash randomization. unset и0 совпали во всех трёх runtime.1/42/4294967295 воспроизведены по исходному LCG; два random-процесса дали разные порядки, их сохранённые hash-secret использованы только для синтетической сверки. Нет утверждения, что hash-secret автора известен.

## Что это меняет для предыдущих исследований

Отрицательные проверки последовательных children не исключают сценарий «Electrum1.7.4 → dict-order CSV → внешнее маскирование по строке». Это не опровержение старых результатов: меняется их область применимости. BX/SX не получают автоматически такую перестановку — сначала нужен конкретный пользовательский путь через данный exporter. Для чистого1.9.8 кусочная receiving/change карта подтверждена, новые неизвестные перестановки не вводятся.

Если доступны MPK, состав пула, импорты и runtime/hash-настройки, порядок1.7.4 получается **из публичных данных**: MPK→raw child public points→raw addresses→dict. Изолированный public_mapper.py получил только эти поля и совпал во всех126 случаях; ни seed, ни приватный master, ни WIF ему не передавались. Для random-режимов hash-secret также был входом; без него эта проверка не обещает единственный порядок.

Если MPK неизвестен, адреса и порядок зависят от каждого master-кандидата. Нельзя сортировать опубликованные puzzle-адреса вместо raw-адресов: это точки уже преобразованных скаляров. Сам порядок не сокращает пространство master и не создаёт новую атаку. При имеющемся MPK прежние условные методы надо запускать с восстановленной картой, а не с i−1.

Время public-only построения259/260 адресов плюс21 карта: от 0.062 до 0.099с на synthetic case; стоимость запуска Python отдельно. Это не скорость полного исторического GUI/synchronize.
