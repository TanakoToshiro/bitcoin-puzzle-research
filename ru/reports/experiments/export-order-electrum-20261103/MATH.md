# EXP-01 — порядок, публичная карта и граница выводов

## От исходного ключа до номера puzzle

В проверяемом сценарии:

```text
seed → old Electrum master s, MPK=sG
     → raw k_(c,j)=(s+H2(decimal(j):decimal(c): || ser64(MPK))) mod n
     → raw uncompressed address_(c,j)
     → таблица Python2 address→WIF
     → CSV-строка i
     → маскирование k_(c,j) по номеру i
```

Здесь i — позиция после перестановки, а не индекс j в получении child.
Сам экспорт Electrum маскирование не выполняет. Это внешний сценарий,
совместимость которого с действиями автора Puzzle не установлена.

## Точная модель таблицы

CPython2.7.9 string hash для ASCII, C long L бит:

```text
x = prefix XOR (first_byte << 7)
for byte in string: x = ((1000003*x) XOR byte) mod 2^L
x = x XOR length XOR suffix; interpret signed long; remap -1 to -2
```

Empty string имеет hash0. Поддерживаемый здесь ASCII unicode даёт тот же hash.
Без hash randomization prefix=suffix=0. Фиксированный PYTHONHASHSEED создаёт
2*sizeof(long) байт LCG214013/2531011, байт=(state>>16)&255. Это hash seed,
а не seed кошелька. OS-random режимы используют больше неизвестных битов:
64бит hash-secret для Windows long32,128бит для Linux long64; это длина полей,
не оценка фактической энтропии конкретного процесса автора.

Initial slot=hash&mask. На коллизиях i=5*i+perturb+1, затем perturb>>=5;
perturb имеет размер size_t и получает sign-extended отрицательный hash.
Начальная таблица8, рост после нового ключа при fill*3>=size*2.
Новый размер — минимальная степень2 строго больше4*used (при used<=50000).
Перестройка читает старые слоты по возрастанию, не историю вставок. Items читает
активные слоты по возрастанию. Delete оставляет dummy, update не вставляет ключ
заново. Тесты ограничены<=1025 строк, веткаused>50000 не подтверждается native-тестом.

Windows x86: long32,size32. Windows amd64: long32,size64. Linux LP64:long64,size64.
Поэтому просто назвать модель «64-битный Python» недостаточно. Никакой
универсальной сортировки поhash, адресу или child-index этой моделью не заменяется.

## Почему MPK достаточно для вычисления raw-адресов

Для известного MPK и(c,j) вычислим публичный offset a_(c,j) и точку

```text
P_(c,j) = MPK + a_(c,j)*G.
```

Из её несжатой сериализации получаем raw-адрес, затем выполняем ровно операции
вставки исторического exporter. Приватный s не нужен. Однако необходимы состав
пула, список/история импортов и профиль hash runtime; их отсутствие оставляет
несколько карт. В данной работе проверено126 полных публичных реконструкций.
Random hash-secret в этих тестах был предоставлен как вход, а не восстановлен.

Публичные ключи и адреса уже маскированных Puzzle задач не заменяют raw-адреса.
Маскирование не сохраняет ни публичную точку, ни HASH160, ни строковый hash Python.

## Что значит изменение прежней проверки

Если старый тест отвергал k_i=F(master,i−1) с определённым маскированием, это
не означает отрицание k_i=F(master,pi(master,profile,pool)[i]). Это разные модели.
Вторая вычислима для кандидата master/MPK, но без него pi обычно неизвестна.
Нельзя свободно подгонять pi по83 известным ключам: допустима только перестановка,
полученная реальным exporter. Нельзя и заранее вычислить одну карту, используя
случайный synthetic master, а потом применить её ко всем остальным.

Порядок сам по себе не уменьшает энтропию seed/master. При правильном публичном
артефакте он устраняет ошибку сопоставления и возвращает применимость условных
методов EL-02. При отсутствии артефакта новый дешёвый путь восстановления master
не получен. Исторический экспорт1.9.8 чистого old account остаётся кусочным
receiving/change списком, в него нельзя переносить dict-перестановку1.7.4.

## Масштабирование

Построение B raw public addresses требует B публичных EC tweaks и хеширований.
Таблица при обычных хешах требует порядкаB времени и памяти; худший случай
коллизий квадратичен и отдельно покрыт synthetic-контролем, не объявлен обычным.
Для нескольких runtime/hash профилей адреса можно переиспользовать; новая
стоимость — построение таблиц. Но другой master меняет все raw-адреса, поэтому
эта подготовка в общем случае повторяется для каждого master-кандидата.

Шесть synthetic cases не задают вероятности изменения порядка и не доказывают,
что любое добавление адреса меняет относительный порядок остальных. В tested
R256→R257 default cases общая подпоследовательность осталась той же; при росте
таблицы/коллизиях изменение возможно и проверено отдельными controls.
