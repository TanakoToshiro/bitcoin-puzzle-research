# CORE-RNG-01 — Bitcoin Core 0.9.3: RNG, официальные сборки, импорт

Дата: 05.11.2026 МСК. Продолжение строки Bitcoin Core в WALLET_COVERAGE_20261104.md.

Задача: отделить обычную генерацию отдельных ключей от внешнего генератора, проверить реальные архивные бинарники и конкретные ошибки обработки RNG/импорта. Перебор пространства ключей или неизвестного состояния OpenSSL не входит в этот эксперимент.

## Зафиксированные материалы

- Core commit `40d20412ff173e8eea2f456fd749663c8cabda18`.
- OpenSSL `OpenSSL_1_0_1i`, commit `2b456034457b58454aae3998a2765b6a5b9bc837`.
- Официальные `bitcoin-0.9.3-linux.tar.gz` и `bitcoin-0.9.3-win.zip`; оба SHA-256 совпали с официальным SHA256SUMS.asc. Подпись PGP не проверялась. SOURCES.json содержит URL, размеры и хеши.
- Из архива запускаются bitcoind Linux32/Linux64/Windows32/Windows64. Они не пересобраны. Старые ОС 2014 года не эмулируются.
- Linux32 использует частную распаковку libc6-i386/lib32stdc++6/lib32gcc-s1 Ubuntu, без установки пакетов в ОС. Метаданные apt и хеши сохранены.

## Проверки бинарников

`audit_binaries.py` использует независимые affine secp256k1 и Base58Check на Python stdlib. Ни адреса, ни WIF не вычисляются через Core для ожидаемого результата. Проверяется каждый ключ в выгрузках.

Каждый запуск: новый каталог `runs/<UTC>-<profile>-<mode>`, `-datadir=.`, regtest, `-listen=0 -connect=0 -dnsseed=0 -discover=0 -upnp=0 -maxconnections=0`. RPC обращается к 127.0.0.1; пароль искусственный и сохранён в команде. Сеть подтверждается regtest genesis и нулём подключений. `getinfo.testnet=false` в этой версии нормально для regtest. Windows получает относительные имена файлов, чтобы кодировка старого приложения не зависела от кириллицы абсолютного пути.

Режим `normal`:

1. Версия, genesis, генерация сжатых ключей, keypool, выдача старого reserve-ключа, refill.
2. Импорт scalar 1 с двумя encodings, n−1, произвольного корректного 128-битного числа; точное сохранение WIF и адреса.
3. Отрицательные контроли: 0, n, 2^256−1, WIF другой сети, raw hex, недопустимый символ Base58 (`0`). Контроль с именем `checksum` использует именно этот символ; отдельный валидный Base58 с неверной контрольной суммой здесь не заявляется.
4. Повторный importprivkey меняет label. Importwallet с датами/равными датами/label/reserve/change; неправильная строка пропускается; повторный importwallet не меняет label.
5. Dumpwallet сортируется по времени, затем числовому uint160 keyid (little-endian относительно байтов HASH160). После перезапуска проверяются все ключи, labels и birthdays.

Режим `restore-encrypt`: восстановление полного dump в новый wallet, сохранение всех исходных ключей, шифрование с искусственным паролем, отказ dumpprivkey при locked wallet, unlock, оба способа импорта в encrypted wallet, второй restart и повторная независимая проверка ключей/birthdays. Дополнительные собственные случайные ключи нового кошелька допустимы.

Режим `invalid-wallet`: отдельный disposable Linux-процесс, импорт WIF с нулевым scalar через importwallet. Ожидаемый ненулевой exit подтверждается assertion в console-log; это положительный контроль ошибки приложения, а не успешный импорт. Windows-авария этим режимом не проверяется.

Linux strace сохраняет openat/read/connect; чтение /dev/urandom в официальных бинарниках отделяется от статического чтения исходников. Качество ядровой энтропии из одного такого наблюдения не выводится.

## RNG-контроль

`prepare_rng_probe.py` извлекает без изменений CKey::Check и CKey::MakeNewKey. Метаданные и хеш извлечения — RNG_EXTRACTION.json. Минимальная оболочка CKey имеет явно обнулённое хранилище; она не воспроизводит все детали исторического размещения объекта в памяти.

`build_rng_probe.sh` собирает OpenSSL 1.0.1i с современным GCC, `linux-x86_64 no-shared no-asm no-dso no-krb5 -fPIC`, и C++14-обвязку. Это сборка исторического алгоритма, не побитовая репродукция Gitian. Исходный архив и извлечённые методы не патчатся.

Link wrappers RAND_bytes/RAND_poll вводят искусственные отказы только внутри тестового процесса. Контроли: границы scalar; retry; успешные байты с return 0/−1; отказ без записи с заранее заданным valid storage; ограниченные 16 неудачных нулевых выдач; реальная OpenSSL без entropy polling; здоровая OpenSSL с обычным polling. Никакие слабые ключи не используются вне теста.

## Процедурные замечания

Самая первая команда Windows64 `-version` оказалась неподдерживаемой: старый daemon начал обычный запуск, создал новый default-каталог и остановился из-за отсутствующего RPC-пароля. Этот пробный запуск не считается изолированным тестом: журнал показывает запрос определения внешнего IP и инициализацию сетевых потоков. Высота осталась 0. Все файлы были созданы между 23:14:04 и 23:14:13 UTC; существующего пользовательского wallet не было по инвентаризации creation times. После проверки отсутствия bitcoind новый каталог целиком перемещён в `incidental-version-probe`, inventory сохранён. Никакие файлы не удалялись. Последующие проверки используют явные ограничения выше.

Два ранних normal-run остановились на неверном ожидании testnet=true; контроль заменён проверкой genesis. Первый Linux32 не стартовал без 32-битного loader; локальные библиотеки устранили причину. Первоначальная C++11-обвязка требовала C++14 для aggregate initialization; это изменение относится только к обвязке. Незавершённые/ошибочные попытки сохранены, но не включаются в принятые проверки.

## Границы вывода

Не проверяются macOS/GUI, каждый исторический компилятор и дистрибутив, изменённые сторонние сборки, старые ядра/CryptoAPI, клоны виртуальных машин, все режимы ENGINE, реальные отказы энтропии на машине автора, повреждённые Berkeley DB, произвольные внешние генераторы. Не выполняются передача монет, генерация блоков, перебор паролей или GPU-поиск. Для применения к автору нужны дополнительные данные о происхождении ключей/состоянии RNG.
