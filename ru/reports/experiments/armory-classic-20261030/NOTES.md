## До запуска — восстановленная формула

Пусть `k_j` — **полный** исходный приватный ключ, `P_j = k_j G`,
`U(P)` — 65 байт `04 || X_BE32 || Y_BE32`, `D(x)=SHA256(SHA256(x))`.
Для постоянного 32-байтного chaincode C:

```text
a_j     = BE_integer(C XOR D(U(P_j)))
k_(j+1) = a_j * k_j mod n
P_(j+1) = a_j * P_j
```

Множитель декодируется big-endian; XOR здесь побайтовый. Нормальная цепочка
хранит один и тот же chaincode, не обновляет его по правилу BIP32. Нулевой ключ —
вырожденный случай, который наша реализация явно отвергает, а не пропускает.
В четырёх контрольных цепочках он не встретился.

### Как получаются root и chaincode

В стандартном создании кошелька root получается через
`SecureBinaryData().GenerateRandom(32, extraEntropy)`. `BTC_PRNG` —
`CryptoPP::AutoSeededX917RNG<CryptoPP::AES>`. Его reseed получает байты из
`OS_GenerateRandomBlock`, с дополнительным смешиванием пользовательской энтропии.
Это не вызов Python MT19937 и не схема с одним timestamp в качестве seed.
Реальное качество энтропии конкретной машины этим чтением кода не проверено.
[Создание кошелька](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/armoryengine/PyBtcWallet.py#L860),
[BTC_PRNG](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/cppForSwig/EncryptionUtils.h#L118),
[reseed](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/cppForSwig/cryptopp/osrng.h#L122).

По умолчанию chaincode выводится из root; явный chaincode также можно передать
при создании. Формула по умолчанию:

```text
d = D(BE32(root))
C = SHA256((d XOR 5c*32) || SHA256((d XOR 36*32) ||
                                  ASCII('Derive Chaincode from Root Key')))
```

Названная `HMAC256` функция использует 32-байтные pads, а стандартный HMAC-SHA256 —
64-байтный блок. Поэтому замена на стандартный `hmac.new` меняет chaincode.
**Это особенность точного воспроизведения, а не найденная криптографическая атака.**
Нельзя приписывать стандартному режиму две независимые 256-битные неизвестные
root и C: C детерминированно зависит от root. Но из этого не следует слабая
энтропия root или возможность его практически восстановить.
[HMAC256](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/armoryengine/ArmoryUtils.py#L1799),
[DeriveChaincodeFromRootKey](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/armoryengine/ArmoryUtils.py#L3392).

### Индексы, change и маскирование

Root имеет chainIndex = −1; первый ребёнок — 0. Обычный новый адрес выдаётся
общим `getNextUnusedAddress()`, который увеличивает индекс на один. Стандартная
сдача обычного кошелька также вызывает этот метод; отдельная BIP44-ветка change
здесь не предполагается. Есть другие настройки выбора сдачи и предварительное
вычисление пула. Поэтому последовательность экспорта создателя puzzle нельзя
восстановить только по номерам задач.
[Индексы и неизменный chaincode](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/armoryengine/PyBtcAddress.py#L750),
[выдача адреса](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/armoryengine/PyBtcWallet.py#L984),
[обычная сдача](https://github.com/etotheipi/BitcoinArmory/blob/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/ui/TxFrames.py#L859).

В stock-цепочке нет маски puzzle. Условное получение
`puzzle_i = 2^(i−1) | (raw_i mod 2^(i−1))` — отдельная операция над экспортом;
следующее звено должно вычисляться из полного raw, если это стандартный Armory.
Подача усечённого puzzle-ключа обратно меняет модель. Несжатый pubkey внутри
Armory не противоречит сжатым адресам puzzle: после маскирования создатель мог
отдельно вычислить сжатую точку нового ключа. Такое происхождение здесь не доказано.

## 10:51:36 — что даёт пара полных ключей и чего нет в puzzle

Для двух соседних **полных** приватных ключей k, k′:

```text
m = k′ * inverse(k, n) mod n
a ∈ {m, m+n}, оставляя только a < 2^256
C = BE32(a) XOR D(U(kG))
```

Это даёт один или два кандидата C. Третий полный ключ позволяет проверить
предсказание; единственность заранее для всех возможных цепочек не утверждается.
В наших пяти положительных случаях C восстановлен однозначно. Пятый специально
использует `a=n+2`: проверено, что вариант m+n не теряется.
Полные результаты контроля — артефакт исходного исследования (`runs/20261030-105108-7ecfb506/recovery.json`; вне снимка).

В сохранённой таблице 83 решений максимальное i=135: наблюдаются лишь 134
младших разряда соответствующего raw, а 122 разрядные позиции не наблюдаются.
У №71 даже найденный puzzle-ключ дал бы 70 младших разрядов raw и оставил 186
позиций; сейчас сам ключ №71 неизвестен. Принудительный старший бит puzzle
во всех подсчётах исключён. Нельзя подставить известный усечённый k в обратную
формулу и объявить стандартный Armory опровергнутым. Нельзя и считать эти
122/186 позиций доказанной независимой энтропией.
Машинный разбор снимка — артефакт исходного исследования (`runs/20261030-105108-7ecfb506/observations.json`; вне снимка).

**Итог: проверенная реконструкция получена, атака и предсказание бита/XOR №71 — нет.**
Не доказаны ни принадлежность puzzle этой цепочке, ни невозможность атаки на неё.
Нет основания начинать произвольный перебор root/дат/слов; нужны дополнительные
исторические данные или конкретный дефект энтропии. Даже известный C без полного
исходного P_j не даёт непосредственно продолжить публичную цепочку из адреса
усечённого puzzle-ключа.
