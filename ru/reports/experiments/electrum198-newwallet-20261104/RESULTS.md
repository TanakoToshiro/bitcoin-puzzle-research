# EL-NW-01 — Electrum 1.9.8 BIP32 / NewWallet

Работа начата 04.11.2026, завершение проверки — 05.11.2026, Europe/Moscow.

**Ветка воспроизведена на историческом CPython 2.7.9 Windows amd64 и Linux64. Практически перебираемого слабого генератора seed не найдено. Настоящие публичные параметры автора Puzzle не найдены; применение восстановления к настоящему Puzzle не выполнено. Electrum не исключён.**

Отдельный пробел из карты покрытия закрыт для перечисленных ниже операций исходников 1.9.8. Это не полный аудит всех поставлявшихся бинарников и GUI. Старые отчёты по 1.7.4/1.9/OldWallet не заменяются.

## Исторический срез и воспроизведение

Commit [`f92b483942d3f8ee51506e0436d9b524db33a336`](https://github.com/spesmilo/electrum/tree/f92b483942d3f8ee51506e0436d9b524db33a336), 16.03.2014, tag 1.9.8. Полный upstream-архив и SHA256 сохранены; восемь ранее использованных файлов сверены с E9. Карта участков — SOURCE_FACTS.json — артефакт исходного исследования (`SOURCE_FACTS.json`; вне снимка), архивы и зависимости — DOWNLOADS.json — артефакт исходного исследования (`DOWNLOADS.json`; вне снимка).

Исполнялись неизменённые модули кошелька, account, bitcoin, mnemonic, commands, transaction; GUI-метод CSV извлечён буквально, подменена только оболочка выбора файла/сообщений. Python-ecdsa 0.11, slowaes 0.1a1, pbkdf2 1.3 подключены из исходных архивов без системной установки. Последний модуль нужен NewWallet, но `setup.py` 1.9.8 не объявляет его в install_requires и архив не содержит его в lib. Поэтому наличие класса в исходниках не доказывает готовность каждого исторического дистрибутива запускать его без дополнительной зависимости.

Кошельки исключительно синтетические, сокеты в стенде запрещены, шифрование файлов проверено тестовым паролем. PyQt4, настоящий интерактивный GUI, сеть и полные установочные пакеты Electrum не запускались. Два профиля используют PYTHONHASHSEED=0; универсальность порядка множества аккаунтов для всех hash-профилей не утверждается.

## Создание, восстановление и точная цепочка

| Операция | Проверенный результат |
|---|---|
| Новый wallet по умолчанию | OldWallet, seed_version=4. NewWallet/version=6 выбирается только при `config.get('bip32') is True`; строка `'true'` недостаточна. |
| CLI | Определение `--bip32` закомментировано; настоящий parser отвергает флаг с exit=2. Вариант через булево значение конфигурации существует; обычный GUI-create следует тому же factory. |
| Entropy | `ecdsa.util.randrange(2^160)`: в проверенной 0.11 по умолчанию os.urandom. Контроль подтвердил запросы по 21 байту и rejection, а не MT/time/32-битное состояние. |
| Mnemonic | SHA256 от 20-байтного entropy+nonce; старое кодирование Electrum со словарём 1626 слов, первые 13 слов. Nonce увеличивается до HMAC-SHA512 с ключом `Seed version`, начинающегося на hex `01`. |
| Seed для BIP32 | PBKDF2-HMAC-SHA512, 2048 итерации, salt `mnemonic`, 64 байта. Пароль шифрования wallet не является mnemonic passphrase; в get_seed передаётся пустая passphrase. |
| Обычные ключи | `m/0'/a/b/i`: a — аккаунт без hardened, b=0 receive или 1 change, i — индекс с нуля. P2PKH и WIF используют сжатый публичный ключ. |
| Restore seed | Hex/обычные 12 старых слов выбирают OldWallet; 13-словная фраза и произвольный непохожий текст могут выбрать NewWallet. Проверка is_seed в from_seed закомментирована: фраза с неверным префиксом принята. Это не свидетельство, что автор использовал слабую фразу. |
| Нормализация | Core применяет strip и NFC. Внутренние пробелы и регистр влияют на PBKDF2; wizard дополнительно переводит ввод в нижний регистр. Это не современный BIP39/NFKD-путь. |

Два соседних тестовых entropy=1 и 2 дали одинаковую mnemonic: nonce=181 и 180 соответственно. Третий вход `(1<<159)+0x123456789abcdef` дал nonce=238 и другую mnemonic. Это ожидаемая коллизия алгоритма «следующее подходящее значение», а не найденное малое пространство.

13 слов здесь содержат первые четыре 32-битных блока и одно слово из следующего: до фильтра не более `2^128 × 1626` вариантов. При идеальной HMAC-модели 8-битный префикс даёт масштаб около 2^131 допустимых фраз; это оценка, не доказательство точной энтропии/равномерности. Основания для полного перебора такой области нет.

## Экспорт, MPK и артефакты

Для чистого NewWallet после change_gap_limit(256) и synchronize экспорт содержит **260 строк данных**: receive 0..255 текущего аккаунта, change 0..2, затем `m/0'/1/0/0` из next_addresses. Заголовок отдельно. Для OldWallet без next_accounts прежний результат 259 не переносится сюда. Все 260 WIF и адресов сверены независимо. Выборочный dumpprivkeys сохраняет переданный порядок и возвращает список списков.

Два аккаунта в проверенных профилях дали блоки a=0, a=1, затем адрес a=2. Это наблюдение конкретных CPython/hash-профилей. Общий порядок аккаунтов задаёт Python2 dict, а не обещание сортировки по номеру. Windows/Linux CSV совпадают по строкам, байтовые SHA различаются из-за перевода строк.

Публичный узел обычного кошелька — **m/0'**, не корень m:

- getmpk возвращает Python-repr пары `(chain_code, K)`, где K — 64 байта x||y без 04.
- from_mpk ожидает `K:chain_code`. Прямой round-trip вывода getmpk завершается ошибкой; переставленная пара с двоеточием создаёт watch-only с теми же адресами.
- При таком watch-only восстановлении cK остаётся пустым (`FIXME` в исходнике). Адреса вычисляются по K, но get_keyID выдаёт неполную строку с пустым compressed K. Это не новый известный MPK автора.
- Полный seeded-wallet формирует `bip32(chain_code,compressed_K,/a/b/i)`. В незавершённом `.txn` KeyID присутствует в input_info, причём input_info — JSON-строка внутри внешнего JSON. При complete=True этот элемент отсутствует. Передача транзакции в блокчейн не переносит эти metadata.

Для этой ветви нужен **K вместе с chain code и верным путём**. Старый 128-hex MPK OldWallet без chain code нельзя объявлять достаточным BIP32-параметром. Xpub и публичный ключ одного puzzle-адреса тоже нельзя без проверки приписывать узлу m/0'.

## Условное восстановление

Независимый recover_public.py — артефакт исходного исследования (`recover_public.py`; вне снимка) принимает явный публичный узел, source/target paths и известный маскированный ключ по модели Puzzle. Он не перебирает seed, не читает wallet и не обращается в сеть. Формула и ограничения — [MATH.md](<MATH.md>).

При известном m/0' public node все a/b/i остаются non-hardened, поэтому суммарные добавки вычисляются публично. Полный исходный child раскрывает приватный узел m/0'. Из маскированного наблюдения с не меньшим числом младших битов получаются до трёх кандидатов целевого маскированного ключа; адрес позволяет их проверить. Это не восстановление исходной mnemonic или родителя m через hardened-границу.

На каждом профиле проверены 12 положительных сценариев receive/change и разных аккаунтов; изменение наблюдаемого бита, chain code или пути даёт 36 отрицательных контролей. Это три входа entropy и **две различные mnemonic**, а не три независимых корня. В отдельном процессе публичный JSON-пример дал 3 кандидата и 1 совпадение с синтетическим адресом. Никакие кандидаты настоящего Puzzle этим результатом не объявлены.

## Дополнительные дефекты выбранного среза

- На точном entropy=`2^160−1` nonce-поиск перешёл за 20 байтов и завершился `TypeError: Odd-length string`. Этот край не даёт практического малого семейства кошельков.
- При принудительном HMAC IL=n private CKD возвращает ключ родителя с новым chain code, вместо пропуска индекса по BIP32. Обычные официальные векторы совпадают; искусственный край не означает частую коллизию.
- Объект BIP32_Account_2of3 реально использует унаследованный redeem_script 2-of-2; отдельный get_redeem_script с 3 ключами не вызывается этим путём. После сохранения/загрузки он создаётся как BIP32_Account_2of2. Проверено исполнением, не исправлялось. Такой CSV может содержать несколько склеенных WIF; он не равен обычной последовательности одиночных ключей.

## MPK автора и применимость к Puzzle

Повторно просмотрен сохранённый текстовый корпус двух исследований вложений по новым точным BIP32-профилям: **71 файл**, с закреплением SHA256. Единственный body с xpub содержит 6 появлений трёх xpub в сообщениях 63965983/63967343, тема 5493466 — отдельный halving tribute puzzle от 19.04.2024. Это не автор исходной серии Bitcoin Puzzle. Совпадений с BIP32 KeyID, master_public_keys, K:chain или парой getmpk в просмотренном тексте нет. Подробности — PUBLIC_ARTIFACT_REVIEW.json — артефакт исходного исследования (`PUBLIC_ARTIFACT_REVIEW.json`; вне снимка).

Это ограниченный повторный просмотр имеющихся текстовых данных, не новый полный веб-поиск, не OCR и не исчерпывающий анализ бинарных архивов. Недоступные источники прежнего архивного аудита остаются недоступными. Достоверный узел автора отсутствует, поэтому реальное восстановление не запущено.

**Решение:** сохранить точную ветвь как проверенную условную модель; массовый перебор не запускать. Для следующего содержательного шага нужен новый артефакт, связывающий автора с K+chain code, либо конкретное доказательство ограниченного источника seed. Штатный Electrum с OS entropy этим исследованием не исключается.

## Проверки и воспроизводимость

ACCEPTANCE.json — артефакт исходного исследования (`ACCEPTANCE.json`; вне снимка) указывает успешные run-каталоги. В каждом: 260 CSV-строк + 15 дополнительных адресов/WIF, независимая Python3-проверка, 6 узлов официального BIP32 vector 1, 12/36 masked recovery-контролей, 15 восстановлений синтетического приватного узла из полного child. Сверены оба runtime executable, python27.dll, исторические модули, зависимости, архивы и входной текстовый корпус.

Повтор: `python -B run_native.py windows-amd64` или `linux64`, затем `python -B verify.py <путь-к-NATIVE.json>`; короткая дополнительная серия — `run_native.py <профиль> extra.py`. Всё пишет новый run-каталог. В Linux требуется существующий WSL Ubuntu-24.04 и подготовленный runtime из соседнего export-order эксперимента. Для публичного примера: `python -B recover_public.py <SYNTHETIC_PUBLIC_INPUT.json> <новый-output.json>`.

Ошибочные подготовительные попытки сохранены отдельно. Исправлены ошибки стенда: old-style классы Python2, один тестовый entropy вне 160-битного диапазона, кодировка кириллического пути в JSON и относительный путь в проверяющем скрипте. Исторические исходники не менялись. Ошибки стенда не учитываются как дефекты Electrum. FINAL_MANIFEST.json — артефакт исходного исследования (`FINAL_MANIFEST.json`; вне снимка) фиксирует итоговые артефакты.
