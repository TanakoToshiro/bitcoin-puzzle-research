## Вердикт

Есть полезное, ещё не выполненное нами направление: построение небольших наборов возможных исходных публичных точек для верхних задач и совместные ограничения нескольких переходов Armory с общим chaincode. Сами публичные ключи №161–256 уже собраны и проверены в E5. Их новое применение не равно обнаружению новых блокчейн-данных или готовой атаке.

### Корректная арифметика

При условной модели d_i = 2^(i−1) + (K_i mod 2^(i−1)), 0 <= K_i < 2^256:

```
K_i = d_i + (t−1)*2^(i−1),  0 <= t < 2^(257−i)
R_i = Q_i + (t−1)*2^(i−1)*G,  Q_i = d_i*G
```

Следовательно, для №256 есть две возможные точки R_256: Q_256 и Q_256−2^255*G. Для №255 — четыре, для №254 — восемь. Всего 14 отдельных точек, но 8*4*2 = 64 сочетания для тройки №254–256. Столько сочетаний можно построить дёшево; проверка существования общего неизвестного chaincode не становится от этого дешёвой.

Это кандидаты на точки K_i*G, не кандидаты на числовые K_i. Если K_i должен быть допустимым приватным скаляром, дополнительно действует 1 <= K_i < n; перечисление точек само по себе не доказывает принадлежность неизвестных скаляров этому интервалу. В групповых вычислениях скаляры берутся по модулю n. Точки на бесконечности исключаются из обычной цепочки публичных ключей.

### Что остаётся трудным в Armory

Для исторического classic Armory из E3 точная зависимость имеет вид:

```
H_i = SHA256(SHA256(uncompressed_SEC(R_i)))
R_(i+1) = BE(C XOR H_i) * R_i
```

Она сверена с закреплённым [исходником 2015 года](https://raw.githubusercontent.com/etotheipi/BitcoinArmory/61a596fa94f9cacf9fb00c4e02d0eb65d8b17513/cppForSwig/EncryptionUtils.cpp), а не только с изменяемой веткой master. В прежнем E3 уже проверены официальные векторы и независимая арифметика; повторять реконструкцию не требуется.

Для одной пары точек получение множителя обычным способом требует дискретного логарифма относительно R_i. Несколько переходов дают дополнительную структуру: общий C, разные известные H_i. Это содержательная постановка, однако быстрого решения из присланного текста не следует.

Можно точно переписать XOR через неизвестные биты c_j цепочного кода. Если h_ij — бит j целого BE(H_i), то:

```
BE(C XOR H_i) = BE(H_i) + sum_j c_j*(1−2*h_ij)*2^j
R_(i+1) − BE(H_i)*R_i = sum_j c_j * [(1−2*h_ij)*2^j*R_i]
```

Это система уравнений с бинарными неизвестными и значениями в группе эллиптической кривой. Она не является системой линейных уравнений над GF(2), доступной прежнему решателю E1. Разбиение 256 неизвестных битов пополам даёт наивный meet-in-the-middle масштаба 2^128 комбинаций в каждой половине; это ориентир для такого метода, не нижняя граница и не доказательство невозможности улучшения. Множество совместных переходов нужно исследовать отдельно.

Даже восстановление C на верхнем фрагменте не показывает, как получить №71: публичная деривация направлена вперёд, а обратный шаг содержит хеш ещё неизвестной предыдущей точки. Нужен отдельный алгоритм обратного восстановления либо доступная начальная точка нужной цепочки и подтверждённая индексация. Armory как исторический источник puzzle не установлен.

### Что в ответе повторяет выполненное

- E5 уже содержит все 96 публичных ключей №161–256 с привязкой к исходным выходам и проверенными raw-транзакциями.
- Проверены 324 выбранные ECDSA-подписи, повторов r нет. Для 15 доступных приватных ключей в транзакции раскрытия 2019 года nonce совпали с RFC6979/HMAC-SHA256 с учётом знака. Поэтому предложение восстановить nonce по известным приватным ключам и сравнить с RFC6979 в этой области уже реализовано.
- Разделение поздних расходов решателей и исторических пакетов уже учтено. Совместное расходование не доказывает личность автора или одинаковое ПО генерации и подписи.
- Предупреждение о нелинейности ограничения d_i(S)*G = Q_i правильно, но не новый способ включения публичных ключей в матрицу MT.

Опора: [итоги E5](<experiments/public-key-forensics-20261030/runs/20261030-114903-5757a87d/CONCLUSION.md>), [итоги E3](<experiments/armory-classic-20261030/runs/20261030-105108-7ecfb506/CONCLUSION.md>), [уточнение терминологии E3](<experiments/armory-classic-20261030/CLARIFICATION.md>). Опубликованные puzzle-решения остаются полными ключами, K_i — отдельная гипотетическая исходная величина.

## Предлагаемое дополнение к следующему циклу

Перед очередным большим seed-перебором провести ограниченную математическую проверку этого направления:

1. Построить наборы исходных точек №254–256 из уже проверенного каталога E5 и сверить независимой арифметикой; расширять к меньшим номерам только при необходимости, поскольку число кандидатов растёт экспоненциально.
2. Зафиксировать точную систему общих XOR-множителей и условия последовательных звеньев. Сначала проверить идентифицируемость и стоимость на уменьшенных группах с независимыми синтетическими цепочками.
3. Сравнивать с отдельным DLP и полным поиском уменьшенного C, учитывать память, число переходов, ложные решения и цену выбора ветвей. Измерять масштабирование по размеру, а не только успешное решение игрушечного примера.
4. Если нет механизма улучшения сложности и пути от верхнего фрагмента к №71, сохранить границу результата и не запускать тяжёлый поиск на secp256k1.
