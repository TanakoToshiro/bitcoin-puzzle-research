# Предложения после E8 и завершения E1d

> Обновление статуса 31.10.2026: пункты 1–3 уже существенно исследованы в E1e/E1f/E1g/E1h/E1k. Этот текст сохраняет первоначальные предложения; текущее покрытие и открытые вопросы — [обзор экспериментов](<EXPERIMENT_REVIEW_20261031.md>). Не считать все пункты ниже ещё не выполненными.

Дата: 30.10.2026, Москва. Статус: предложения; новые вычисления по этому документу не запускались. Приоритет означает ценность следующей проверки, а не установленную вероятность успеха или мировую новизну.

Основание: [E1d завершён, 40/40](<experiments/mt-all-targets-20261030/runs/20261030-131459-93a3e1c9/CONCLUSION.md>). Некоторые MT-модели дают ограничения, например для №108 остаётся 76 свободных координат вместо 107. Это всё ещё больше полного пространства №71. Другая совместимая модель допускает все 8953 неизвестных бита; найденные ограничения нельзя считать реальными битами без установления генератора. [E8](<experiments/mpk-source-search-20261030/RESULTS.md>) исключил конкретные варианты Electrum от №256, но не любые схемы от этого ключа.

## 1. Совместить MT-ограничения с исходными №161–256

Области: линейная алгебра над GF(2), восстановление состояния PRNG, ограничения на скаляры эллиптической кривой.

E1d исследовал 77 нерешённых целей №1–160. Построить отдельные проекции для первоначальных №161–256, публичные точки которых проверены E5. Сначала работать со схемами без неизвестных отказов. Определить размерность пространств для самих полных puzzle-ключей и связанных ключей, не подменяя их гипотетическими исходными raw. Использовать известную маску с точным переходом к публичным точкам; верхние исходные точки E6H дают отдельные конечные альтернативы.

Первый этап — только ранги, структура ограничений и стоимость проверки по публичной точке. Само наличие точки Q не раскрывает младшие биты скаляра. Проверить предложенный способ объединения на синтетических группах/малых задачах и сравнить с базовым решением DLP; большое сокращение пространства не гарантирует быстрого алгоритма. Если не возникает малая размерность или структура, дающая измеримое преимущество, закончить этап оценкой сложности без большого перебора.

## 2. Какие ограничения переживают неизвестные отказы

Области: символьное исполнение, линейные инварианты, объединение пространств состояний.

Для выбранного API собирать расширяемое семейство допустимых историй. Вычислять ограничения, верные во всём объединении, включая правые части уравнений: по аффинной оболочке объединения, а не пересечением допустимых состояний. Сначала сравнить уже сохранённые истории, затем контролируемо добавлять новые. Разделить инварианты конкретного API и инварианты объединения разных API. Сохранение формулы на выборке историй не доказывает её для всех возможных историй; окончательный вывод требует покрытия/доказательства. Не повторять взвешенный пилот E1c как доказательство полноты.

## 3. Проверить способность моделей предсказывать известные решения

Области: выбор моделей, диагностическое исключение наблюдений, проверка предсказаний.

По заранее фиксированным блокам исключать часть опубликованных решений из ограничений. Для каждого исключённого ключа сначала проверить, даёт ли модель вообще нетривиальное предсказание; если весь ключ свободен, такая проверка не подтверждает модель. Там, где есть фиксированные биты/XOR, сравнить их с исключёнными значениями. Включить синтетические наборы настоящего генератора и независимых случайных ключей. Это ретроспективная диагностика: решения уже были доступны и использовались в исследовании, поэтому это не новый слепой тест и не основание для наивной оценки значимости после отбора моделей.

## 4. Исторический JavaScript и реальный путь энтропии

Области: история реализаций PRNG, браузерная криптография, реконструкция программ.

Первичный источник V8 описывает MWC1616 с 64-битным состоянием, применявшийся до конца 2015 года: [публикация разработчиков](https://v8.dev/blog/math-random). Это отдельное семейство, не равное уже проверенным MT, Java Random48 и xorshift32. Для января 2015 нельзя автоматически использовать современный алгоритм Math.random.

Начать с точной исторической реализации MWC1616 и двух фиксированных способов построения 256-битного значения: байты и 32-битные слова, с явной моделью преобразования double. Контроли должны исполнять исторический код. Восстанавливать состояние по ограничениям до выделения бюджета на перебор. Отдельно исследовать конкретные исторические wallet-библиотеки: Math.random мог лишь пополнять пул, после чего шли дополнительные смешивания/генератор потока. Отказ прямой модели не исключает такую библиотеку. Связь создателя puzzle с JavaScript пока не установлена.

## 5. Конечные публичные конструкции от №256

Области: воспроизведение самодельных схем деривации, сериализация и доменное разделение.

Низкозатратный, но слабее обоснованный тест идеи пользователя: строка адреса №256, его HASH160, SEC-публичный ключ как публичный seed; несколько заранее фиксированных SHA-256/HMAC-схем с номером задачи или хеш-цепочкой. Проверить конкретные текстовые/бинарные представления и обе направления нумерации, оставив отдельные известные ключи для проверки. Не подбирать десятки преобразований после каждого промаха. Успех требует точного совпадения нескольких независимых адресов/решений. Предыдущий E8 этой постановки не охватывал.

## 6. Историческая атрибуция кошелька и дополнительные параметры

Области: анализ первичных исходников и форматов, происхождение публичных артефактов.

Искать конкретный след программы/формата с привязкой к автору или времени создания: оригинальное вложение, экспорт, исходный скрипт, MPK/xpub. Сравнивать признаки ранних транзакций с историческими программами только как слабые свидетельства: программа подписи/отправки могла отличаться от генератора ключей. Для BIP32 одной точки недостаточно — публичная деривация использует также chaincode; это видно из [спецификации BIP32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki). Произвольный перебор chaincode не становится эффективным от выбора №256 корнем.

## Рекомендуемый порядок

Сначала 1–3: они используют новые результаты E1d и уже проверенные данные. Затем 4 как новое семейство с историческим основанием. Пункт 5 можно выполнить отдельным коротким циклом. Пункт 6 продолжать при конкретных зацепках, не бесконечным повторением общих веб-запросов.

Низкий приоритет сейчас: новые ML-предикторы HASH160 без независимого сигнала; повторение seed32 в уже покрытых схемах; увеличение тайм-аута полной криптографической SMT-задачи без нового разложения; поиск числовой близости адресов. Новые проверки должны заканчиваться либо воспроизводимым ограничением/прогнозом, либо явной границей покрытия и оценкой стоимости продолжения.
