# Задание для отдельного чата: BX 2.0 → BIP32 на RTX 3070 Ti

Подготовлено 01.11.2026, Москва. Это самодостаточная передача текущей задачи, а не отчёт о готовой CUDA-реализации.

## Что нужно сделать

**Перенести существующий CPU-поиск BX → BIP32 на локальную NVIDIA GeForce RTX 3070 Ti Laptop GPU, проверить корректность и измерить реальную скорость всех 16 схем.** После замеров оценить полный проход пространства начальных состояний и целесообразность следующего испытания на арендованной RTX 4090.

Последнее указание пользователя: перенос выполнять в отдельном чате; текущему чату поручено только сохранить это задание. На момент передачи новый GPU-код не написан, сборка CUDA для этой цепочки не выполнялась, GPU-поиск не запускался. Выполнены только чтение исходников и проверка доступности CUDA/GPU.

Работать автономно в рамках реализации, локальных тестов и ограниченного бенчмарка. Не арендовать сервер, не запускать полный многочасовой поиск без отдельного задания. Не создавать другой чат автоматически.

## Зачем мы это проверяем

Проект исследует публичный Bitcoin Puzzle. Цель — **любая нерешённая задача**, в том числе с известным публичным ключом; №71 не обязателен. Пользователь ищет закономерности и слабости генерации, а не только ускорение перебора приватных ключей или kangaroo.

Текущая гипотеза: автор мог использовать исторически доступный инструмент **Libbitcoin Explorer (bx) 2.0.0**, собранный с GNU libstdc++, для получения слабого seed, затем получать дочерние приватные ключи BIP32 и приводить их к диапазонам puzzle маскированием.

**Связь автора puzzle с BX не установлена.** Обнаружена подходящая ограниченная гипотеза, которую можно проверить полностью. Даже очень быстрый полный проход может дать отрицательный ответ. Вероятность успеха количественно не оценена.

Известные опубликованные приватные ключи — **полные решения соответствующих puzzle**, а не опубликованные обрезки неизвестного приватного ключа. Не путать это с нашей гипотезой: до маскирования внутри предполагаемого генератора мог существовать другой, полный 256-битный BIP32 child scalar. Его младшие биты должны согласоваться с опубликованными решениями.

## Точная вычислительная гипотеза

Исторический BX 2.0.0: commit `aae99b278fdbfa31005cfa083ccbbf909212cbe4`, 14.12.2014. В `src/utility/utility.cpp`:

> Исполняемый код/команды опущены в документационной копии.


Для рассматриваемой GNU libstdc++ `default_random_engine` — `minstd_rand0`:

```text
p = 2147483647
initial_state = seed % p; если 0, заменить на 1
state = 16807 * state mod p
next_byte = state mod 255
```

Критически важно: **mod 255, не mod 256**; байт берётся из **нового** состояния. Полное пространство различных нормализованных начальных состояний — **1..2147483646 включительно**, то есть `2^31 − 2`. Это не пространство приватных ключей puzzle и не неизвестное произвольное 256-битное состояние кошелька.

Проверяем две длины entropy: **16 и 32 байта**. Оба потока для одного состояния имеют общий префикс. Эти байты подаются **напрямую в BIP32 master**, без мнемоники, BIP39 и PBKDF2:

```text
I = HMAC-SHA512(key="Bitcoin seed", data=entropy)
master_private = parse256(I[0:32])
master_chain_code = I[32:64]
```

Обычный CKDpriv BIP32, сжатые SEC public keys:

```text
для hardened: data = 0x00 || ser256(parent_private) || ser32(index)
для normal:   data = compressed_public(parent_private) || ser32(index)
I = HMAC-SHA512(key=parent_chain_code, data=data)
child_private = (parse256(I[0:32]) + parent_private) mod n
child_chain_code = I[32:64]
```

Здесь `n = FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141`, `ser32`/`ser256` big-endian. Проверять недопустимые master/child, включая `IL >= n` и нулевой child. В текущей гипотезе retry/skip не задан: такой случай — явная ошибка/неполный блок, а не тихое отбрасывание кандидата. IL=0 для child сам по себе допустим, если итоговый child ненулевой.

Для каждой длины entropy проверяются четыре **родительских пути**:

| Номер path в коде | Родитель | Индексы |
|---:|---|---|
| 0 | `m` | `[]` |
| 1 | `m/0` | `[0]` |
| 2 | `m/0'/0` | `[0x80000000, 0]` |
| 3 | `m/0'/1` | `[0x80000000, 1]` |

После родителя идёт ещё **один non-hardened child** с индексом:

```text
j = puzzle_number − 1 + offset, offset ∈ {0, 1}
```

Таким образом, всего `2 длины × 4 родителя × 2 offset = 16 схем`. Puzzle — соседние children одного родителя внутри схемы, а не последовательное углубление пути.

Предполагаемое преобразование BIP32 child scalar `k_i` в решение puzzle `i`:

```text
d_i = 2^(i−1) + (k_i mod 2^(i−1))
```

Принудительный старший бит не является наблюдением исходного child. Сохранять настоящие номера puzzle: пропуски в известных решениях не сжимают индексы.

## Как проверять кандидата

Для подбора/отбрасывания используются известные решения **№1–50**. Решения **№51 и выше** — только отложенная проверка после совпадения всех обучающих.

Текущий быстрый CPU-режим сначала сравнивает **49 младших битов child для №50**. Почти все state–scheme отбрасываются сразу. Если №50 совпал, проверить остальные №1–50, затем отложенные решения. №1 не содержит свободных битов и не фильтрует состояние.

GPU может делать ранний фильтр, а редкие выжившие — проходить полную проверку на CPU. В таком варианте надо явно описать разделение работы, измерять всю цепочку с передачами/проверкой и подтвердить положительными контролями, что кандидаты не теряются. Не объявлять проверку одного фильтра самостоятельным доказательством восстановления состояния.

При полном совпадении требуется независимое вычисление приватных значений и адресов предполагаемых целей. Не объявлять ключ найденным только по раннему фильтру. Обычный массовый поиск не требует HASH160 для каждого кандидата: здесь проверяется соответствие известным скалярам, адреса нужны для окончательной проверки.

Это экстраполяция по коротким/средним измерениям, не фактически завершённый 18-часовой проход. Всего 21 бенчмарк, повторы интервалов не прибавлялись к уникальному покрытию. Ранний фильтр №50 на одной паре дал лишь ×1,054; на другом контрольном интервале был немного медленнее. Главный выигрыш native версии — общий код и многопоточность, а не сам порядок сравнения.

Микропрофиль одного CPU-потока:

- новый сжатый public key из скаляра: около **26,33 мкс**;
- HMAC-SHA512 по 37 байтам с кэшированным ipad/opad: **0,433 мкс**;
- CKDpriv с готовым public key родителя: **0,503 мкс**;
- RNG + master: **2,606 мкс**.

На обычное отбрасываемое состояние во всех 16 схемах: **10 fixed-base умножений G на скаляр** и **26 HMAC-SHA512** (2 master, 8 промежуточных children, 16 final-filter children). Родитель `m/0'` общий для ветвей 0 и 1, его не следует вычислять дважды. Приближённый счёт по микрозамерам относит около 94% стоимости компонентов к public key; это не точное профилирование полного ядра.

Не использовать заявленные пользователем **6,2 млрд адресных проверок/с на 4090** как скорость данной цепочки. Здесь новые несвязанные скаляры и зависимые уровни BIP32, а не последовательные шаги по соседним точкам.

Создать новый каталог, например:

```text

```

Не менять замороженные E9/E9b. Хранить код, протокол, сборочные логи, библиотеки/заимствования, тестовые результаты, ошибки и замеры внутри нового каталога. Вести `README.md`, обновляемый `RESULTS.md` и журнал промежуточных выводов. Числовые таблицы формировать из JSON/CSV, изменения выводов добавлять с датой. После завершения обновить общие `research/puzzle71-hypotheses/README.md` и `NOTES.md`.

Рабочая архитектура на выбор исполнителя:

1. GPU получает интервал начальных состояний; генерирует entropy и BIP32 master.
2. Выполняет нужные промежуточные CKDpriv/public-key операции. Переиспользует общий родитель `m/0'`, публичные ключи и HMAC-состояния там, где это выгодно.
3. Для всех 16 схем проверяет final child для №50. Выжившие состояния и схемы сохраняет без потерь/переполнения буфера.
4. Полная проверка обучения/holdout может выполняться CPU-эталоном для редких выживших. Время этой части учитывать отдельно и в полной скорости.

Возможный исходный fixed-base подход — таблицы окон G и Jacobian accumulation с нормализацией. Размер окна, batch inversion, fused/staged kernels и распределение работы по потокам выбирать по корректности и измерению. Не требуется сразу достигать рекорда: сначала проверяемая первая GPU-версия.

## Обязательные проверки до основного бенчмарка

Не ограничиваться результатом «на GPU тоже ноль совпадений».

1. **SHA512/HMAC:** сравнить с независимым CPU для используемых размеров и граничных/случайных входов. Проверить endian, длину сообщения, padding, длину HMAC key.
2. **Скаляры и EC:** сравнить public keys и сложение mod n с libsecp256k1; случаи 1, n−1, перенос через 256 бит, результат 0, IL=0, IL≥n, нулевые оконные цифры, случайные скаляры. Непригодные входы не должны превращаться в успешные вычисления.
3. **Промежуточные узлы:** сверить entropy, master, parents, chain codes, compressed public keys и children по `EXPECTED.json` E9b. Там 10 состояний × 8 родителей × 9 children = **720 дочерних узлов**, включая hardened индексы. Исторические 14 BX-векторов также должны проходить.
4. **Положительные end-to-end контроли:** восстановить заложенные synthetic states во всех 16 схемах, включая близкие к концу пространства. Отрицательная мутация обучающих данных должна отвергаться; испорченный holdout должен отличаться от полного совпадения. Проверить, что GPU-фильтр передаёт кандидата на CPU, а не теряет его.
5. **CPU/GPU сопоставление:** сравнить final-child low bits/флаги на заметной фиксированной выборке, не только hits. Для реального интервала сравнить итоговый набор кандидатов; на искусственных данных гарантированно есть выжившие.
6. **Границы и учёт:** начало/конец пространства, count не кратный block size, последний частичный batch, пустой/недопустимый диапазон; не пропускать и не дублировать состояния при checkpoint/resume. Переполнение candidate buffer — ошибка/повтор блока, не тихая потеря.
7. **CUDA-ошибки:** проверять ошибки allocation, launch, async execution; при доступности использовать compute-sanitizer на небольшом наборе. Проблемный блок не засчитывать как покрытый.

Успех контролей подтверждает реализацию модели, а не факт применения BX автором puzzle.

## Как замерять и что ожидать от результата

Основная единица: **состояний в секунду при проверке всех 16 схем**. Можно дополнительно показывать state–scheme/с, но не путать их; последнее значение в 16 раз больше.

Разделить:

- создание/загрузку таблиц и прогрев;
- чистое GPU-время (CUDA events с корректной синхронизацией);
- передачи данных, сбор кандидатов и CPU-проверку;
- полное wall time рабочего batch/серии;
- пиковую VRAM и параметры запуска.

Сначала небольшой диапазон для калибровки. Затем минимум несколько повторов на различных участках пространства и достаточно длительная серия после прогрева. Записать все измерения, не выбирать только максимальную скорость. Основной GPU-бенчмарк разумно ограничить **15 минутами** после разработки/контролей; полный seed-поиск не входит в это задание. Если первая версия медленнее CPU, честно сохранить результат и указать конкретное узкое место.

Сохранять для каждого запуска ID, интервалы `[start, stop)`, число состояний/схем, код и хэши входов, настройки CUDA, версии, телеметрию, времена и результаты. Пересекающиеся benchmark-интервалы не суммировать как новое уникальное покрытие. Законченное с теми же входами не пересчитывать при resume; намеренный повтор для измерения производительности обозначать отдельно.

Формула полного прохода:

```text
hours = 2147483646 / (states_per_second_all16 * 3600)
```

Ориентиры, **не прогноз скорости GPU**:

| Скорость всех 16 схем | Время полного пространства |
|---:|---:|
| 25 000 состояний/с | 23,86 ч |
| 100 000 состояний/с | 5,97 ч |
| 250 000 состояний/с | 2,39 ч |
| 1 000 000 состояний/с | 35,79 мин |

Главный ожидаемый научный результат этого этапа: **проверяемая GPU-реализация и измеренная стоимость полного теста гипотезы**, а не обязательная находка ключа. Если реальные кандидаты появятся, сохранить всё и отдельно независимо проверить их.

GPU-порт полезен, если заметно сокращает уже доступные **18,49 CPU-часа** либо позволяет дешёво расширять число схем в будущих экспериментах. Не расширять молча сами 16 схем в процессе бенчмарка — это отдельная версия исследования.

## Оценка 4090 и критерии завершения

В E9b сохранены официальные страницы Runpod: `experiments/bx-native-search-20261101/sources/`. При просмотре 01.11.2026 в прайс-листе было **$0,89/ч**; на странице модели одновременно встречалась другая рекламная цифра. Это исходная оценка, а не гарантированная текущая цена/доступность. Перед новой рекомендацией аренды сверить цену заново. Аренду не оформлять.

По скорости 3070 Ti можно обосновать целесообразность короткого испытания 4090, но нельзя выдавать предположительный коэффициент масштабирования за измерение. Показать необходимую скорость для желаемого времени и условную стоимость отдельно от фактического результата локальной карты.

Задача завершена, когда:

- CUDA-версия собрана и реально выполнена на локальной 3070 Ti Laptop;
- положительные, отрицательные и промежуточные сравнения прошли либо конкретная неисправность документирована без ложных результатов;
- сохранены воспроизводимые замеры всей цепочки и честное сравнение с CPU;
- рассчитано время полного прохода и описаны узкие места/следующий шаг;
- README содержит команды сборки, проверки, бенчмарка и продолжения; RESULTS и общий журнал обновлены;
- E9/E9b и рабочие проекты с checkpoints остались неизменными.

В финальном ответе пользователю главное: реальная скорость GPU по всем 16 схемам, ускорение/замедление против CPU, ожидаемое время полного прохода, что именно проверено и есть ли основание переходить к 4090. Дать ссылки на сохранённые отчёты.
